Detection and incident response — how I think about it

Event vs incident

An event is any observable occurrence. An incident is an event that violates policy or threatens confidentiality, integrity or availability. Not every event is an incident; part of the analyst’s job is telling them apart.

NIST SP 800-61 incident-response lifecycle

  1. Preparation — policies, playbooks, tooling, training, contact lists.
  2. Detection & analysis — recognise events, triage, verify, classify severity, scope the incident.
  3. Containment, eradication & recovery — stop the bleeding, remove the attacker’s foothold, restore service.
  4. Post-incident activity — lessons learned, playbook updates, evidence retention, root-cause analysis.

Documentation discipline: chain of custody (evidence integrity), incident handler’s journal (timestamped notes), formal ticket per incident.

Triage — prioritise alerts by impact (business criticality) and urgency (attacker progress).

The 5 W’s I capture on every incident: Who, What, When, Where, Why. See my incident handler’s journal entries below for real examples.

Network monitoring and analysis

Why network telemetry matters

Attackers must communicate. The network sees it before the endpoint does. Packet captures are the ground truth when logs are ambiguous.

tcpdump — command-line packet capture

Uses BPF filter syntax. Common patterns:

# Capture on eth0 for a specific host
tcpdump -i eth0 host 10.0.0.5

# Capture only port 443
tcpdump -i eth0 port 443

# Capture SSH inbound and write to a pcap file
tcpdump -i eth0 tcp and dst port 22 -w capture.pcap

# Read a saved pcap
tcpdump -r capture.pcap

Runs on the command line with a low resource footprint — ideal for remote / headless / Linux-based environments where a GUI isn’t available.

Wireshark — GUI packet analyser

Different filter syntax (display filters). Common patterns:

ip.addr == 10.0.0.5
tcp.port == 443
http.request.method == "POST"
dns.qry.name contains "malicious"

Wireshark’s value in cybersecurity: capture and analyse network traffic, filter by protocol / IP / port / other criteria, follow streams (TCP / UDP / HTTP), and isolate specific events. Widely used for network troubleshooting, incident response, forensic investigations and security monitoring. This is a tool I already use daily on 5G RAN signalling — same skills, different protocols.

Suricata — open-source IDS/IPS

Signature-based intrusion detection / prevention. Rules describe suspicious patterns; matches generate alerts (typically JSON) that stream into a SIEM.

IoCs vs IoAs

  • Indicators of Compromise (IoCs) — observable artifacts: IP addresses, file hashes, domain names, URLs, filenames.
  • Indicators of Attack (IoAs) — behaviours suggesting an attacker is present (bulk failed logins, unusual outbound C2).

Incident investigation with logs and SIEM

Log types and what each proves

  • Network — firewall, DNS, proxy.
  • Endpoint — Sysmon, EDR.
  • Authentication — AD, IdP, SSO.
  • Application — web-server access, API access.
  • Cloud audit — CloudTrail, GCP audit.

Syslog is the standardised log format (timestamp, host, program, message). Structured (JSON) vs unstructured logs affect how easy they are to search.

Splunk — SPL query patterns I use

index=main sourcetype=access_combined status=403
index=auth EventCode=4625 | stats count by src_ip user

Chronicle — YARA-L and UDM search

Chronicle uses YARA-L rules and the Unified Data Model (UDM) for searches. Same investigative discipline as Splunk with different syntax.

MITRE ATT&CK

Matrix of adversary tactics (why they act) and techniques (how they act). Mapping observed behaviour to ATT&CK gives the SOC a shared vocabulary.

Threat-intelligence tools I’ve used

VirusTotal — investigative tool that analyses files and URLs for malicious content (viruses, worms, trojans and more). Very helpful for quickly checking whether an IoC like a website or file hash has been reported malicious by others in the community.

Deliverables I produced

Phishing incident-response playbook (version 1.0)

Purpose: help level-one SOC analysts respond to phishing incidents appropriately and on time.

Flow I built:

  1. Step 1 — Receive phishing alert. Process begins when an alert ticket indicates a phishing attempt has been detected.
  2. Step 2 — Evaluate the alert. Investigate details and relevant logs. Capture:
    • Severity: Low (no escalation), Medium (may need escalation), High (immediate escalation).
    • Receiver: email address, IP address.
    • Sender: email address, IP address.
    • Subject line, message body.
    • Attachments or links.
    Rule: never open links / attachments on your device unless you’re in an authorised, isolated environment (sandbox / VM).
  3. Step 3.0 — Does the email contain links or attachments? If yes → Step 3.1. If no → Step 4.
  4. Step 3.1 — Are the links/attachments malicious? Check reputation via threat-intel tools like VirusTotal (hash the file, look up the URL). If not malicious → Step 4.
  5. Step 3.2 — Update ticket & escalate. If malicious, summarise findings, mark ticket Escalated, notify a level-two SOC analyst.
  6. Step 4 — Close the alert ticket. Only if the email has no links/attachments or those links/attachments are confirmed not malicious. Include an investigation summary and the reason for closing.

SOC alert ticket A-2703 — phishing with malicious attachment

Alert: SERVER-MAIL Phishing attempt possible download of malware — severity Medium.

Email details I extracted:

  • From: “Def Communications” <76tguyhh6tgftrt7tg.su>, IP 114.114.114.114
  • To: hr@inergy.com, IP 176.157.125.93
  • Subject: Re: Infrastructure Egnieer role (typo present)
  • Body claims to be from “Clyde West” applying for an engineer role; attaches a password-protected file bfsvc.exe with password paradise10789.
  • Known-malicious file hash (SHA-256): 54e6ea47eb04634d3e87fd7787e2136ccfbcc80ade34f246a12cf93bab527f6b

Ticket comments I wrote:

The alert detected that an employee downloaded and opened a malicious file from a phishing email. There is an inconsistency between the sender’s email address (76tguyhh6tgftrt7tg.su), the name used in the email body (Clyde West), and the sender’s displayed name (Def Communications). The email body and subject line contained grammatical errors. The body also included a password-protected attachment (bfsvc.exe) which was downloaded and opened on the affected machine. Having previously investigated the file hash, it is confirmed to be a known malicious file. Alert severity is Medium. Given these findings, I escalated the ticket to a level-two SOC analyst for further action.

Incident final report — forced-browsing data breach (50,000 customer records)

Executive summary: on December 28, 2022 at 7:20 pm PT, an attacker gained unauthorised access to customer PII and financial data. Approximately 50,000 customer records were affected. Estimated financial impact: $100,000. Incident is now closed.

Timeline:

  • Dec 22, 2022, 3:13 pm PT — an employee received an email from an external address claiming to have stolen customer data. Extortion demand: $25,000 in cryptocurrency. Employee assumed it was spam and deleted it.
  • Dec 28, 2022 — same employee received a second email from the same sender, this time with a sample of the stolen data and an increased demand of $50,000.
  • Same day — employee notified the security team; investigation began.
  • Dec 28–31, 2022 — security team focused on determining how the data was stolen and the extent of the theft.

Investigation & root cause: a forced-browsing vulnerability in the e-commerce web application. The attacker manipulated the order number in the URL of a purchase-confirmation page and pulled thousands of customer transaction records. Web-app access logs confirmed a single log source generating an exceptionally high volume of sequentially listed customer orders.

Response & remediation: collaborated with PR to disclose the breach to affected customers; offered free identity-protection services.

Recommendations I delivered:

  • Perform routine vulnerability scans and penetration testing.
  • Implement URL allowlisting — allow access only to a specified set of URLs and automatically block requests outside that range.
  • Ensure only authenticated users can access protected content via proper access-control mechanisms.

Incident handler’s journal — four entries I wrote

Entry #1 — Ransomware incident at a health-care company.

  • 5 W’s: Who = organised group of unethical hackers. What = ransomware. When = Tuesday 9:00 am. Where = health-care company. Why = phishing gave unauthorised access; ransomware encrypted org data; ransom demanded for the decryption key. Motive: financial gain.
  • Phase mapping: Detection & Analysis (org first detected the ransomware and contacted others for technical assistance). Containment / Eradication / Recovery (org shut down computer systems but had to contact others for help to eradicate + recover).

Entry #2 — Investigating a suspicious file hash with VirusTotal.

  • Tool used: VirusTotal — analyses files and URLs for malicious content and reports what other researchers have found.
  • 5 W’s: Who = unknown threat actor using the Flagpro malware. What = a phishing email attachment with SHA-256 hash 54e6ea47eb04634d3e87fd7787e2136ccfbcc80ade34f246a12cf93bab527f6b — flagged as malicious by 50 security vendors. When = Wed 6/30/2026, 9:30 am. Where = employee’s computer at a financial-services company. Why = employee downloaded and executed the file; the malware establishes C2 comms, captures user input, and sends HTTP requests, enabling data theft / further malicious action.
  • TTPs observed: Command & Control (C2), Input Capture, HTTP Requests.
  • Indicators of compromise (IoCs): Domain org.misecure.com, IP 207.148.109.242, file hash 287d612e29b71c90aa54947313810a25.
  • Recommended response: isolate infected systems, block the malicious domain and IP, quarantine the file, update endpoint security tools, run a full environment scan for additional infections.

Entry #3 — Phishing email with a password-protected malicious attachment (ticket A-2703, see above). Recommended actions: isolate the affected system, block the malicious hash + sender, scan for additional compromise, reset affected user credentials if necessary, deliver phishing-awareness training.

Entry #4 — Forced-browsing customer-data breach (final-report scenario, see above). Full 5 W’s captured; recommendations: routine vuln scans + pen tests, URL allowlisting, enforce authenticated access only.

Investigation-findings presentation

Built a short deck to communicate investigation output to stakeholders — timeline, IoCs, business impact, containment actions, remediation. The right level of detail for a management audience without losing the technical facts a peer analyst needs.

Pitfalls I stay aware of

  • Opening suspicious attachments on your own device — always sandbox / VM. Password-protected attachments are a specific evasion technique (they hide the payload from automated email scanners so the recipient has to open it manually).
  • Confusing IoC and IoA — IoCs are artefacts (IP, hash, domain); IoAs are behaviours (bulk failed logins). Both matter, but they drive different detections.
  • Closing a ticket without investigating attachments — the playbook exists so no analyst skips the reputation check on a link or file.
  • Missing sender-identity inconsistencies — sender domain that doesn’t match displayed name, body signed with a different name, grammatical errors — all classic phishing tells.
  • Not documenting an incident cleanly — without a proper handler’s journal, the post-mortem is guesswork and the next analyst is no faster.

Additional detection & IR concepts I know

Detection design

  • Host-based IDS (HIDS) — runs on the endpoint and inspects that host’s file, process and log activity. Network-based IDS (NIDS) — sits on a network segment and inspects traffic (Suricata). A mature program uses both.
  • Signature-based analysis — matches against known IoC / pattern signatures. Fast, low-false-positive, but blind to zero-days.
  • Anomaly-based analysis — baselines “normal” behaviour and alerts on deviations. Catches novel attacks; noisier (more false positives).
  • Honeypot — a decoy system that looks valuable but has no real business use. Any interaction with it is inherently suspicious — high-signal early warning.
  • Zero-day — vulnerability the vendor doesn’t yet know about; no patch exists. Detection here relies on behaviour, not signatures.

Alert-quality vocabulary

  • True positive — alert fires and the incident is real.
  • False positive — alert fires but nothing bad is happening; wastes analyst time.
  • True negative — nothing bad, no alert; the desired steady state.
  • False negative — something bad is happening but nothing alerted; the most dangerous of the four.

Tuning a SOC is really about pushing false positives and false negatives towards zero at the same time.

Threat hunting vs threat intelligence

  • Threat hunting — proactive search for adversaries already inside the environment that haven’t triggered an alert. Hypothesis-driven, uses ATT&CK as a playbook.
  • Threat intelligence — contextual information about adversaries (TTPs, IoCs, campaigns) that feeds detection rules.
  • Open-source intelligence (OSINT) — intelligence collected from publicly available sources.
  • Common Event Format (CEF) — a standard format for log messages; makes it easier to normalise events across sources feeding into a SIEM.

Digital forensics

  • Digital forensics — the discipline of identifying, preserving, analysing and presenting digital evidence in a legally defensible way.
  • Chain of custody — documented handoff of evidence from collection to court, showing who had it, when, and what they did. Broken chain of custody = evidence potentially inadmissible.
  • Protecting and preserving evidence — work from images, not originals; hash both to prove nothing changed.

Incident-response operational terms

  • Incident response plan — the org-wide document defining roles, contacts and procedures for handling incidents. Precedes any individual playbook.
  • Escalation policy — formal rules for who gets notified, at what severity, and on what timeline.
  • Incident escalation — the act of raising the incident to a higher tier / team when it exceeds your authority or scope.
  • Improper usage — an incident type where an authorised user violates acceptable-use policy (data misuse, unauthorised installations) — distinct from an external breach and often handled with HR involvement.
  • Unauthorised access — an outsider (or an insider outside their role) getting into a system they shouldn’t.
  • Lessons learned meeting — blame-free post-incident review capturing what happened, what worked, what to improve, and action items with owners + dates.
  • Final report — the definitive record of an incident, its impact, timeline, response, and recommendations. Formal deliverable often shared beyond the SOC.
  • Resiliency — the property of a system that lets it withstand and recover from adverse events. Includes redundancy, backups, failover, disaster recovery.
  • Business continuity plan (BCP) vs Disaster recovery plan (DRP) — BCP keeps the business running during the disruption; DRP restores IT / infrastructure back to normal.
  • Log analysis — systematically reading logs to answer investigative questions: when, who, what, from where, how.
  • Network log analysis — log-analysis specifically focused on network telemetry (firewall, DNS, proxy).
  • Visual dashboard — the SIEM UI that turns raw indexed data into charts / tables / timelines for quick analyst comprehension.
