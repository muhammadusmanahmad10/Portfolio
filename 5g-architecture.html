5G System Architecture & Interfaces

5G replaces LTE's "boxes and tunnels" with a Service-Based Architecture (SBA) in the core — every function is an independent Network Function (NF) exposing services over HTTP/2. The NG-RAN (gNB / ng-eNB) connects to the 5G Core (5GC) via standardized reference points N1–N6, and the core NFs talk to each other over the SBA bus. Knowing which NF owns what — and which interface carries which procedure — is how I navigate every cross-team escalation.

The full picture

Network Functions — who does what, in plain words

NF (full form)In plain words
AMF — Access & Mobility Management FunctionThe UE’s "front door" to the core. Terminates NAS, handles registration, mobility, paging and access authentication (with AUSF). It’s what sits on N1 (to the UE) and N2 (to the gNB).
SMF — Session Management FunctionManages the UE’s data session (PDU session). It assigns the UE an IP address and controls the user-traffic path. The SMF talks to the UPF over the N4 interface using PFCP (Packet Forwarding Control Protocol). Through PFCP the SMF creates, modifies and deletes forwarding rules — the instructions that tell the UPF how to handle the UE’s traffic (where to send the packets, which path to use, and when to start or stop forwarding). This is how the UE’s data reliably reaches its destination — the public Internet, an enterprise network, or a specific service.
UPF — User Plane FunctionThe actual data-forwarding box. Anchors the GTP-U tunnel from the gNB (N3), pushes the UE’s traffic out to the Data Network (N6), enforces QoS and the rules SMF gave it.
AUSF — Authentication Server FunctionAuthenticates the UE using its SIM credentials. It runs security procedures such as 5G-AKA (5G Authentication and Key Agreement) or EAP-AKA′ (Extensible Authentication Protocol – Authentication and Key Agreement) to verify the subscriber and securely allow access to the 5G network.
UDM / UDR — Unified Data Management / RepositoryThe subscriber database. UDM is the service layer that serves authentication and subscription data to AMF / SMF / AUSF; UDR is the data layer underneath where the actual records live — in plain words:
  • Profiles — who the subscriber is: SUPI/IMSI, allowed PLMNs / slices, the data plan they bought, allowed services (voice, SMS, roaming).
  • Policy data — the QoS / slice / charging rules tied to that subscriber: which 5QI, ARP, GBR / MBR they get, which slice S-NSSAI they can use, what counts toward their billing.
  • App data — state that other functions store about the user: e.g. last-known location for E911, group membership, third-party AF data (parameter provisioning, expected UE behaviour). UDR is just the storage; UDM, PCF and NEF read/write it through standard service operations.
PCF — Policy Control FunctionThe QoS / charging / slice rulebook. It decides what policies apply to each session and pushes them to SMF (N7) and AMF. In plain words:
  • QoS policy — how each service is treated on the radio and core: which 5QI (service class), ARP (priority), and GBR / MBR (guaranteed / max bitrate) the SMF should install. So voice gets 5QI 1 with low-latency treatment, video gets 5QI 7/9, WPS gets 5QI 128 with high ARP, and so on.
  • Slice policy — which slice (S-NSSAI) the UE is allowed on and what runs inside that slice: each slice has its own DNN, QoS rules and isolation, so an enterprise slice (e.g. 7000 / 7001) gets a different treatment from the default consumer slice.
  • Charging policy — rules sent to the CHF about how to count usage (online / offline, per-flow, per-slice).
Policy page →
NRF — Network Repository FunctionThe 5G core’s service registry / "phone book". Every NF registers itself with the NRF, and other NFs use it to discover who is currently available.
NSSF — Network Slice Selection FunctionThe slice picker. At registration it tells the network which slice (S-NSSAI) and which AMF set should serve this UE.
NEF — Network Exposure FunctionThe safe API gateway that exposes 5G core capabilities to external Application Functions (AFs) without giving them direct access to the core. An AF is just any application that wants to talk to the 5G network — typical examples that sit outside the operator and come in through NEF:
  • IoT / fleet platforms — e.g. a logistics company’s tracker cloud asking "is this UE reachable right now?" or "tell me when it comes online", and provisioning expected UE behaviour (low data volume, mostly idle) so the network optimises for it.
  • V2X / connected-car application servers — subscribing to UE location and triggering safety messages.
  • Enterprise traffic / DNN steering — a corporate app requesting that traffic for its UEs goes via a specific DNN or edge UPF.
  • Content delivery / streaming providers — requesting a temporary QoS uplift (e.g. better 5QI) for a live event.
  • Public-safety / mission-critical apps — subscribing to UE location and reachability events to support emergency operations.
  • Smart-meter / utility platforms — checking reachability before sending bulk readings, and configuring monitoring events.
Internal AFs (operator-owned, like IMS / P-CSCF for VoNR) can talk to the core directly because they sit in the trusted domain; external AFs always go through the NEF, which enforces authentication, authorisation and rate-limiting on every request.
CHF — Charging FunctionThe billing engine. Handles online and offline charging (the 5G replacement for LTE’s OCS/OFCS); SMF talks to it over N40.
NWDAF — Network Data Analytics FunctionThe analytics / ML brain of the core. Collects data from other NFs and feeds insights back (load balancing, slice selection, anomaly detection, mobility prediction).
SMSF · BSF · LMF — SMS Function / Binding Support Function / Location Management FunctionSMSF carries SMS over NAS; BSF is the PCF-binding helper (so other NFs find the right PCF for a given session); LMF is the positioning brain — computes where the UE is for emergency services (see E911).

Reference points & service-based interfaces

InterfaceBetweenProtocol / purpose
N1UE ↔ AMFNAS signalling (registration, security, mobility)
N2gNB ↔ AMFNGAP (over SCTP) — control plane to RAN. NG HO →
N3gNB ↔ UPFGTP-U (UDP/2152) — user plane
N4SMF ↔ UPFPFCP — SMF programs UPF forwarding rules. The three core rule types, in plain words:
  • PDR (Packet Detection Rule) — "this is the packet I’m looking for." A match filter (TEID, IP 5-tuple, interface) that tells the UPF: if a packet matches this, treat it as part of this flow.
  • FAR (Forwarding Action Rule) — "this is what to do with that packet." Forward it (and to which interface / next hop), drop it, buffer it, or duplicate it (e.g. for lawful intercept).
  • QER (QoS Enforcement Rule) — "and these are the speed limits." Policing / shaping bandwidth caps (MBR, GBR) and DSCP marking for the matched flow.
Together, a PDR / FAR / QER triplet is one direction of one flow on the UPF: match this → do this → at this rate.
N6UPF ↔ Data NetworkIP toward external DN
N7 · N5SMF↔PCF · AF↔PCFPolicy decisions. N7 is how the PCF tells the SMF which QoS / charging rules to install on the user’s session. N5 is how an Application Function feeds policy input to the PCF — the most common one being the IMS P-CSCF acting as AF for VoNR:
  • A SIP INVITE arrives at the P-CSCF; its SDP negotiates what the call actually needs — e.g. audio with codec EVS / AMR-WB at a given bitrate, plus video (for ViNR), plus call type (normal, emergency, WPS).
  • The P-CSCF translates that SIP/SDP information into media-level policy hints and sends them to the PCF over N5: media type (audio / video), required bandwidth, priority indicators (emergency, WPS), and the IP 5-tuple of the RTP flow.
  • The PCF turns those hints into concrete QoS rules — the right 5QI (5QI 1 for voice, 5QI 2 for video, 5QI 5 for IMS signalling), the right ARP (higher for emergency / WPS), GBR / MBR — and pushes them to the SMF over N7.
  • The SMF then programs the UPF over N4 with the matching PDR / FAR / QER, so the RTP packets get the right bearer treatment end-to-end.
In short: N5 is how SIP knows what to ask for, and N7 is how the network actually delivers it. Policy →

Service-Based Architecture (SBA) in one paragraph

Inside the core, NFs no longer use Diameter or point-to-point reference points only — they expose services (e.g. Namf_Communication, Nsmf_PDUSession, Npcf_SMPolicyControl) as REST APIs over HTTP/2 + JSON, and find each other through the NRF. Reference-point notation (N11, N7, N8, …) and service notation (Namf, Nsmf, Npcf, …) describe the same conversations from two angles. This is why a 5G core can scale and evolve like a cloud-native system — and why understanding the NF/interface map matters for debugging anything that crosses the RAN/core boundary.

The three pieces in plain words:

  • HTTP/2 — the same web protocol your browser uses, in its faster version 2. It lets one TCP connection carry many requests / responses at the same time (multiplexing), compresses headers, and can stream data efficiently. That’s why a single NF-to-NF connection can carry hundreds of overlapping service calls without becoming a bottleneck.
  • REST API — a simple "ask-and-answer" style of communication where one service calls another using basic web verbs: GET (read), POST (create), PUT (update), DELETE (remove), against a clean URL like /namf-comm/v1/ue-contexts/{id}. So when the AMF wants to ask the SMF to set up a session, it’s essentially making a web call — just like a website talks to a backend.
  • JSON — JavaScript Object Notation, a human-readable text format for structured data: simple "key": "value" pairs grouped into objects and lists. The body of every NF service call is a JSON document, which makes it easy to read in a packet capture and easy for any programming language to parse.

So when you hear "5G core is cloud-native": it’s because the NFs talk to each other the same way modern web micro-services do — REST calls (HTTP/2) carrying JSON, discovered through a registry (NRF) — and that’s what lets the core scale, upgrade, and self-heal like a cloud system.

How I use this in my work

Most cross-domain incidents I escalate live exactly on this map. The AMF relative-capacity attach failure sat on N2 between gNB and AMF; the slice / QoS-flow issues trace back to PCF→SMF→UPF rule installation; E911 location rides AMF↔LMF↔GMLC. Knowing the right NF and interface lets me hand a precise, evidence-backed case to the right team in one shot — instead of "the core isn't working."
