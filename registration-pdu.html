5G SA Registration & PDU Session

Before a UE can do anything on 5G SA it must register (authenticate to the AMF and establish a security context) and then bring up a PDU session (a data path through the UPF). Most "UE won't work" tickets are really a break somewhere in this chain — RRC, NAS, security, or session setup. I validate the full sequence and root-cause the failures at packet level.

3GPP TS 24.501 (5G NAS) 3GPP TS 38.331 (RRC) 3GPP TS 23.502 (procedures) Validated on a live 5G SA Femto deployment

Case study — iPhones preferring LTE: the BWPS attach failure

Symptom
An iPhone (iOS 18.7) would not attach to the 5G SA femto and kept preferring LTE band 71.
Root cause
BWPS (bandwidth-part power saving — which divides the carrier into ~20 MHz chunks to preserve battery) was not enabled at the femto. Without it, the device’s expected BWP behaviour wasn’t satisfied, so it declined the femto and stayed on LTE.
Fix
Enabled the BWPS feature on the femto — the iPhone then attached cleanly.
Same root cause hit a budget Android handset too
A separate budget-tier Android handset was also failing to attach. The device supports NR carrier bandwidths of 20 / 40 / 60 / 80 MHz but not the full 100 MHz. The femto was running on a 100 MHz carrier, and without BWPS there was no way for the device to operate on a narrower BWP within that cell, so it stayed off. After BWPS was enabled, the femto exposed a narrower BWP that the device could use, and the same handset attached without issue.

Takeaway: device attach behaviour is sensitive to BWP / feature config. I keep a device matrix and band-lock UEs to isolate "network vs handset" quickly. The BWPS / BWP path is configured during ZTP — see the ZTP & IPsec page for how the cell’s RF / BWP configuration is provisioned.

Case study — RRC establishment failures at the femto

Duplicate C-RNTI

RRC establishment failed because the femto assigned a duplicate C-RNTI. Two UEs contending for the same cell-radio identity can't both proceed — caught at RRC setup in the trace.

IPsec / DPD timeout under load

RRC establishment failed because the IPsec tunnel was down (DPD timeout) under high load — the femto stopped sending requests to the security gateway, so signalling couldn't reach the core.

Case study — non-VoNR device wrongly attaching

The femto is VoNR-only, so a non-VoNR device should be blocked from attaching (otherwise it would camp but be unable to make voice calls). I found a non-VoNR device was attaching because the blocking feature wasn't enabled at the AMF. Once enabled, the AMF rejected non-VoNR devices at registration (e.g. an iPhone 14 without VoNR support was correctly rejected), and such devices fall back to the macro layer — which is the intended, safe behaviour for emergency calls too.

Other attach-path issues I isolated

  • Access-class barring on the SIM caused a congestion test to fail — the SIM's access class wasn't enabled, so the UE was barred when it shouldn't have been.
  • Intermittent DHCP IP allocation broke OAM tunnel establishment; root cause was the DHCP server not processing requests correctly. After clearing leases (and a policy change to only assign IPs with full reachability to all required security-gateway IPs), the issue cleared.
  • State transitions: validated idle ↔ connected ↔ inactive ↔ idle, plus MO/MT voice/video/data in both idle and connected mode.
    How RRC_INACTIVE works (short version): when the gNB releases a connected UE with a Suspend configuration, the UE moves into RRC_INACTIVE instead of all the way to RRC_IDLE — it keeps its UE context, security keys and bearer state cached at the last serving gNB. While inactive the UE is allowed to move within a RAN-based Notification Area (RNA) without telling the network; when it crosses an RNA boundary or its periodic RNAU timer expires it sends an RNA Update (RNAU). If the gNB accepts the RNAU, the UE stays in RRC_INACTIVE; if the UE doesn’t get a Suspend config when released, or if it doesn’t get an RNAU response in time, it falls back to RRC_IDLE.
    Why INACTIVE beats IDLE: resuming from INACTIVE is much faster and lighter than re-attaching from IDLE — the UE just sends an RRC Resume Request and the gNB reactivates the cached context, so the UE goes back to data in a few signalling messages instead of running a full registration + security + PDU-session re-setup. Same battery saving as IDLE on the UE side, but near-CONNECTED resume latency — ideal for bursty / intermittent traffic.
  • Latency: control-plane (idle→connected, MO & MT) and user-plane (ICMP ping, 32-byte and 1400-byte packets).

Case study — femto 5G SA → 5G NSA (macro) handover using the existing LTE macro as the EN-DC anchor

To validate 5G SA → 5G NSA mobility, I avoided piping a new macro signal to save time by reusing the existing LTE macro used for IRAT testing and the existing 5G SA macro used for inter-frequency handover testing. Working with the macro team, I provisioned an additional NR carrier as an NSA alongside the existing 5G SA cell and configured the LTE macro from the other site as the EN-DC anchor. This enabled the macro to broadcast LTE (anchor) + NR (SCG) using the existing RF path and cabling.

Validation: I validated the complete 5G SA → 5G NSA handover flow from the femto, confirming successful transition to the LTE anchor, correct NR SCG addition, and uninterrupted service continuity. Reusing the existing macro infrastructure eliminated the need to deploy and pipe a separate macro site, while maintaining a consistent test environment across SA, LTE IRAT, and NSA mobility scenarios.

Case study — UE saw MIB in the RF chamber but couldn’t register (wrong RF piping)

Symptom
Inside the RF chamber the UE clearly decoded the MIB on the cell — it knew the cell existed, read the SSB and saw the broadcast — but it could not complete NAS registration. Calls to attach failed even though the air interface looked alive from the broadcast side.
Investigation
Decoding MIB only proves DL reachability on the SSB. To go further (RACH, RRC setup, NAS registration) the UE has to be able to transmit on the cell’s UL antenna ports and have those signals reach the gNB’s RX path. Checked the RF piping between the RRUs and the chamber attenuator network and compared port-by-port against the cell’s antenna-port configuration on the gNB side.
Root cause
The RRU ports were mis-piped — the cables out of the RRUs were connected to ports that didn’t match the antenna-port mapping the cell was configured for. DL SSB still reached the UE on whichever port was active, so MIB decoded fine; but the UE’s UL (PRACH preamble during RACH) was landing on the wrong RX branch / not on the configured port at all, so the RACH preamble never reached the cell’s receiver and registration couldn’t proceed.
Fix
Re-piped the RRU ports to match the cell’s antenna-port configuration. After the correction the UE’s RACH was received, RRC Setup completed, and NAS Registration / PDU Session Establishment ran cleanly.
Concept & takeaway
"Sees MIB but can’t register" almost always means a UL-path problem, not a coverage problem. DL broadcast (SSB + MIB) can succeed on a partial / wrong port chain because it only needs one good DL path. Registration also requires a working UL RACH on the configured port. Takeaway: when broadcast decodes but RACH fails, suspect RF piping / antenna-port mismatch before re-tuning the cell.

Field notes & common pitfalls

  • Read MIB/SIB1 first. Many "attach" issues are really cell-selection/broadcast issues before NAS ever starts.
  • BWP / power-saving features gate device attach. Devices that don’t support the cell’s full bandwidth (e.g. handsets that top out at 80 MHz on a 100 MHz NR cell) and Apple devices that prefer LTE both rely on BWP / BWPS being correctly configured on the femto — without it they decline the cell.
  • VoNR-only cells need explicit non-VoNR blocking at the AMF, or the wrong devices camp.
