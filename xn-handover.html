Mobility · Intra-NR Xn Handover

Xn Handover Validation in 5G SA

An Xn handover is a direct gNB-to-gNB handover in 5G Standalone: the source gNB hands the UE to a neighbour gNB over the Xn interface (XnAP signalling), and the data path to the 5G core is re-pointed afterward with a single NGAP Path Switch to the AMF. It is the lowest-latency mobility procedure in SA because the two gNBs coordinate directly instead of routing the prepare phase through the core.

3GPP TS 38.423 (XnAP) 3GPP TS 38.331 (NR RRC) 3GPP TS 23.502 (Procedures) Validated on a live 5G SA Femto deployment (band n41)

When Xn is used vs NG

Xn is selected when a direct Xn interface exists between source and target gNB and both gNBs are served by the same AMF set. If there is no Xn link, or the target is under a different AMF, the network falls back to NG (N2) handover, where the AMF coordinates the prepare phase. This single rule — same AMF set + Xn up — is the first thing I check when an Xn handover fails.

Xn structure — Xn-C and Xn-U

The standard Xn interface (3GPP TS 38.420 / 38.423 / 38.424) has two planes:

PlaneProtocolCarries
Xn-C (control plane)XnAP / SCTP / IPHandover prep, UE-context transfer, RAN configuration update, Xn setup.
Xn-U (user plane)GTP-U / UDP / IPDL data forwarding from source to target during HO to avoid packet loss.

Signalling flow

💡 Validation anchor: a complete, successful Xn handover collapses to a clean two-message NG signature in the AMF trace — Path Switch Request followed by Path Switch Request Acknowledge. That is exactly the pair my Python automation keys on (see below).

What I check at each step

1
Measurement Report — UE reports neighbour RSRP/RSRQ crossing the A3 offset. I confirm the target cell is present in the ANR/neighbour relation table on the source before expecting any HO.
2
XnAP Handover Request — Source gNB sends the target the UE context and a transparent RRCReconfiguration container. This IE is where the SRB-information interop issue lived (case study below).
3
Handover Request Acknowledge — Target admits the UE and returns the prepared RRC config. Failure here usually means admission control / resource rejection at the target.
4
RRCReconfiguration (to UE) — Source forwards the HO command to the UE. I verify SRB/DRB and security key (NCC) continuity so the UE can sync to the target without re-auth.
5
RRCReconfigurationComplete — UE does RACH to the target and confirms. This is the radio-side success marker; for a VoNR + data session I confirm service continuity here (no audio gap, no stalled bearer).
6–7
NGAP Path Switch Request / Ack — Target asks the AMF to re-point the UPF GTP-U tunnel to itself. The Ack means the user-plane path is now on the target. My automation reports the HO successful only when this pair correlates.
8
XnAP UE Context Release — AMF/target signal the source to free the UE context. I verify no stale bearer remains on the source (the PDUSessionResourceList should match the active sessions).

Case study — Xn won't come up: SCTP source-port mismatch

Symptom
Xn interface between a third-party macro gNB and the femto would not establish in the lab — even though IP was pingable both ways, the identical Xn config worked in production, and Xn worked fine against a different macro vendor in the same lab.
Investigation
Took tcpdump on both ends. The femto was sending SCTP INIT to the macro’s destination port 38422 (the registered XnAP SCTP port) from dynamic source ports (e.g. 56422, 37642), which is the standard SCTP behaviour. No INIT-ACK ever came back from the macro — meaning the INIT wasn’t even reaching the macro’s SCTP stack.
Root cause
Not IP routing. The macro vendor’s firewall rule in front of its SCTP stack was filtering inbound SCTP INITs by source port and only allowing INITs sourced from port 38422 — so the femto’s dynamic-source-port INITs were being dropped before they ever reached the SCTP layer. The other macro vendor in the same lab had a more permissive firewall rule and accepted any source port, which is why the same femto worked there. In production, neighbour-side firewalls had already been pre-provisioned to permit the femto’s traffic, so the lab cold-start was the only place this surfaced.
Fix
The macro vendor updated the firewall rule on their side to accept inbound SCTP INITs to port 38422 regardless of source port. After that, INIT / INIT-ACK exchanged, HEARTBEATs appeared, and Xn became stable.

Takeaway: separate IP reachability from SCTP association behaviour — a pingable link with a dead Xn is almost always SCTP or IPsec, not routing.

Case study — the SRB criticalExtension 3GPP-compliance dispute

Symptom
NR Xn HO (macro → femto) failing. The femto vendor reported the target wasn't receiving SRB info in the criticalExtension IE of the RRCReconfiguration inside the XnAP Handover Request, so SRB/PDCP context couldn't be built — and questioned whether the macro side was 3GPP-compliant.
Standards analysis
Reviewed TS 38.331 + TS 38.423. RRCReconfiguration is UE-facing even in Xn HO; radioBearerConfig / srb-ToAddModList are optional when SRBs are unchanged; XnAP treats the RRC container as transparent and does not require the target to derive SRB state. Conclusion: the macro-side behaviour was fully 3GPP-compliant.
Resolution
Reframed it as a vendor interop alignment, not a standards gap. The femto side updated its logic to also read SRB info from the nonCriticalExtension; the macro side included SRB info explicitly. NR Xn HO stabilised, SRB/PDCP context built correctly.

Why it matters: being able to read the spec and tell a vendor "your peer is compliant, the dependency is on your side" — politely and with the clause references — is the difference between a closed ticket and a month of finger-pointing.

Case study — hand-in failing at RRCReconfiguration (no voice / no data after HO)

Symptom
On hand-in to the femto (macro → femto, Xn HO), the prepare phase ran clean (XnAP Handover Request / Ack exchanged, target admitted the UE), but the UE never completed sync to the target. The trace showed the RRCReconfiguration (the HO command, sent UE-facing by the source) going out, but no RRCReconfigurationComplete arrived back at the target. Result: the UE either fell back to the source cell or hit RLF, and after the moment of switch there was no voice and no data.
Where the failure sits in the flow
Inside an Xn HO the source gNB packages the new SRB / DRB / security / BWP configuration into the UE-facing RRCReconfiguration (carried transparently inside the XnAP Handover Request) and forwards it to the UE. The UE has to apply that configuration, RACH to the target, and reply with RRCReconfigurationComplete. If anything in the prepared config doesn’t match what the UE / target can actually run — security keys, SRB/DRB IDs, PDCP/RLC parameters, BWP, MAC config — the procedure stalls at this step and voice/data fail because no bearer ever comes up at the target.
What to look at in Wireshark
Decode the RRCReconfiguration container itself (the IE inside the Handover Request from the source — the same byte sequence that gets relayed to the UE) and walk the configuration: securityConfig / nextHopChainingCount, radioBearerConfig & srb/drb-ToAddModList, masterCellGroup, and the BWP / PDCP / RLC parameters. Correlate that against what the target actually expects on its admission side. Most hand-in RRCReconfiguration failures trace back to a mismatch in one of those blocks (or to a target-side admission rejection that surfaces only after the UE tries to apply the config).
Concept & takeaway
"Prepare passed but UE never completed" is a different bug class from "Xn / prepare failed". The XnAP signalling is fine — the problem is in the contents of the RRC container the source built for the UE. Takeaway: when hand-in stalls at RRCReconfiguration with no Complete on the target side, decode the RRC container in the Handover Request and verify the security context, bearer IDs and PDCP/RLC config line up with what the target supports — that’s where the post-HO "no voice / no data" symptom comes from.

How I validate it at scale — Python + tshark automation

Rather than eyeballing every capture, I wrote a tshark-driven script that correlates the Xn handover's NG signature (Path Switch Request → Path Switch Request Acknowledge) per UE, emits a CSV with frame numbers, source/dest IPs and copy-paste Wireshark filters, and prints a PASS/FAIL summary. It turns a manual packet hunt into a repeatable, auditable check.

# Xn HO validator — correlates Path Switch Request / Ack from a PCAP (illustrative)
import subprocess, csv

FILTER = 'ngap.procedureCode == 3'   # PathSwitchRequest family
fields = ["frame.number","ip.src","ip.dst","ngap.procedureCode","ngap.RAN_UE_NGAP_ID"]

cmd = ["tshark","-r",capture,"-Y",FILTER] + sum((["-T","fields"],),()) \
      + sum((["-e",f] for f in fields),[])
rows = subprocess.run(cmd, capture_output=True, text=True).stdout.splitlines()

# → "Handover Successful over XN interface"  |  else FAIL with the missing leg
📈 Companion scripts I built using the same pattern: NG handover validator (Handover Required → Notify → UE Context Release), 5G SA registration / PDU-session validator (ngap && nas-5gs), and a WPS-user verifier (RRC establishment cause, 5QI/ARP, slice ID, IMEISV). Net effect: what used to be a slow, manual, multi-step packet hunt becomes a repeatable check that returns a standardized PASS/FAIL in seconds.

Field notes & common pitfalls

  • Xn requires the same AMF set. If source and target sit under different AMF sets, Xn HO fails — the network must use NG handover (which can do inter-AMF relocation) instead. (I hit exactly this: HO failing until we confirmed both sites were in the same AMF set.)
  • Pingable ≠ Xn up. SCTP source-port and IPsec context can block the association while ICMP succeeds.
  • Auto-Xn must be enabled at the peer. One failure was simply auto-Xn-creation disabled on the macro side; another was a traffic-selector mismatch (10.0.0.0 vs 42.0.0.0) configured on the source side while creating the Xn interface toward the SeGW — the protected subnet didn't match the peer's, so traffic was dropped after the gateway.
  • RRCReconfiguration is transparent to XnAP. The target doesn't reconstruct SRB state from XnAP — SRB continuity comes from RRC + security-context transfer.
  • Handout can pass while hand-in fails if the femto cells aren't in the macro's neighbour relations — fixed by driving an attenuator sweep to force a measurement report and let ANR build the relation.
