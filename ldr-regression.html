Legacy Device Regression (LDR) Testing

A 5G SA femto must work with the devices people actually carry — iPhones, Samsung, Google Pixel, Motorola, and other vendor handsets — across many models and OS versions. LDR (Legacy Device Regression) testing is the disciplined sweep across that device matrix on every software change, so a regression in one model is caught before it hits a real user.

What I run on every device, every cycle

  • Attach & registration — successful camp on the femto, SIB read, NAS registration accept.
  • VoNR voice — outgoing and incoming calls, RTT, ViNR (video), SMS-over-IMS.
  • Data — TCP/HTTP throughput, ping latency, ICMP, app-level (e.g. Instagram-feed scroll sanity).
  • WPS & slicing — priority access works, 5QI/ARP/slice IDs applied correctly.
  • Handover — Xn / NG / IRAT mobility, idle-mode reselection (IMCR), redirect-with-release.
  • E911 — SIM and SIM-less, including the non-VoNR fallback to macro for non-supported devices.

Real device issues I root-caused

iPhone preferring LTE B71 (iOS 18.7)

iPhone wouldn’t camp on the femto, kept preferring LTE band 71. Root cause was BWPS not enabled — once corrected, the iPhone attached cleanly.

Android handset — OS-version prerequisite

An Android device wouldn’t attach. Root cause was the handset running an older OS version that didn’t meet the femto’s minimum supported OS level for SA registration. A device-software prerequisite, not a network defect — captured and documented so the next regression cycle doesn’t re-investigate.

iPhone 14 — non-VoNR device rejection

iPhone 14 (no VoNR support) was rightly rejected by the AMF on this VoNR-only femto. Validated the behaviour and confirmed E911 still works via macro layer fall-back.

iPhone 16 Pro / 17 — UL-throughput behaviour

All SA-capable iPhones except iPhone 16 Pro / iPhone 17 fall back to LTE NSA for peak UL throughput (Apple's "send UL via LTE" strategy). Only iPhone 16 Pro / 17 support 2L SU-MIMO on N41 or UE NR-CA and stay on SA. Documented per-device behaviour so the regression report explains the difference, not flags a fault.

How I run it as a regression discipline

  • Whitelisting for E911 — UEs are whitelisted at the LMF / GMLC so E911 tests proceed without false rejection.
  • Band-locking — UE band-locked to the band under test to isolate the femto behaviour from device-side band steering.
  • Trace per device — Wireshark / XCAL5 capture per UE per test, so an issue can be re-attributed (network vs device) on review.
  • Pass / fail per device, per case — published as a regression matrix so a model-specific issue is visible immediately.

Why LDR is non-negotiable

A femto can pass every functional test on three reference devices and still fail for real users tomorrow if a new iOS release, a new One UI version, or a budget-brand modem firmware change shifts behaviour. LDR is what protects the product against that — and what a 5G SA validation engineer is accountable for delivering before any GA / lab-exit decision.
