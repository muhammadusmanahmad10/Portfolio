Assets, Threats and Vulnerabilities

What we’re protecting (assets), how attackers think (threats), where they get in (vulnerabilities), and the crypto, IAM and threat-modelling primitives that hold it all together. Includes the concrete deliverables I produced: a PASTA threat model, an access-control review, a data-leak analysis, a parking-lot USB investigation, and a home asset inventory.

Assets and how I classify them

An asset is anything of value to the organisation:

  • Digital — data, credentials, source code, cryptographic keys.
  • Physical — servers, laptops, badges, USB drives.
  • Human — employees, contractors.
  • Intellectual property — trade secrets, patents, designs.

Asset classification levels — public, internal, confidential, restricted. Handling / storage / transmission controls scale with the level.

Data states and the control that fits each:

  • At rest — disk / database encryption (AES-256).
  • In transit — TLS, IPsec, SSH.
  • In use — access control, memory protection, confidential computing.

PII / SPII / PHI — PII is any info that infers identity; SPII is a stricter subset (SSN, biometrics, financial); PHI is protected health information. Regulation treats each differently.

Cryptography I understand

  • Symmetric encryption — one shared key for encrypt / decrypt. Fast. Examples: AES-128 / AES-256, legacy DES / 3DES. Key distribution is the hard part.
  • Asymmetric encryption — a key pair (public / private). Anyone can encrypt with the public key; only the private key holder can decrypt. Examples: RSA, ECC, DH. Slower — used for key exchange and digital signatures.
  • Hashing — one-way function; produces a fixed-length digest. Used for integrity, not confidentiality. MD5 and SHA-1 are broken; use SHA-256 / SHA-512. HMAC adds a shared secret so integrity is authenticated.
  • Public Key Infrastructure (PKI) — digital certificates issued by Certificate Authorities (CAs). A certificate binds a public key to an identity. Chain of trust: leaf → intermediate → root CA.
  • TLS handshake at high level — client hello → server hello + cert → verify cert chain → key exchange → encrypted channel.

Where this ties to my RAN work: the 5G security stack uses these primitives daily — SUPI/SUCI concealment uses ECIES (asymmetric); 5G-AKA is a mutual authentication protocol; the key hierarchy (K → K_AUSF → K_SEAF → K_AMF → K_gNB) uses HMAC-SHA256 KDFs.

Identity and Access Management (IAM)

The four components of IAM I always name:

  • Identification — who claims to be who (username).
  • Authentication — prove the claim (password, MFA token, biometric, certificate).
  • Authorisation — what the identity is allowed to do (RBAC, ABAC).
  • Accounting / auditing — log every access decision.

Related controls I know: SSO, MFA, RBAC, principle of least privilege, automatic access revocation, regular privilege audits.

Threats, vulnerabilities, and the vulnerability-management lifecycle

  • Threat = potential cause of harm. Vulnerability = weakness that a threat can exploit. Risk = likelihood × impact when a threat meets a vulnerability. You need both a vuln and a threat for a risk to exist.
  • Attack surface vs attack vector: the surface is all the entry points; a vector is a specific path an attacker uses.
  • The vulnerability-management lifecycle: Identify → Assess → Prioritise → Remediate → Verify → Report.
  • Sources I use: CVE identifiers, NVD (national vulnerability database), CVSS scoring (0.0–10.0), vendor advisories.
  • Common vulnerability categories: mis-configuration, unpatched software, weak credentials, insecure defaults, injection flaws (SQL / command / LDAP / XSS), broken access control.
  • OWASP Top 10 web-app risks: broken access control, cryptographic failures, injection, insecure design, security misconfiguration, vulnerable and outdated components, identification & authentication failures, software & data integrity failures, security logging & monitoring failures, server-side request forgery (SSRF).

How attackers attack

Malware families

  • Virus — needs a user to execute; attaches to a host file.
  • Worm — self-propagates over the network without user action.
  • Trojan — hides inside legitimate software.
  • Ransomware — encrypts data and demands payment.
  • Spyware / adware — exfiltrates behaviour or serves ads.
  • Rootkit — hides in the kernel to survive.
  • Botnet — network of compromised hosts under C2.
  • Cryptojacker — steals CPU/GPU to mine cryptocurrency.

Social engineering

  • Phishing (mass email), spear phishing (targeted), whaling (executives).
  • Smishing (SMS), vishing (voice).
  • Business Email Compromise (BEC).
  • Pretexting, baiting, tailgating, quid pro quo.

Web-based attacks

  • SQL injection, XSS (reflected / stored / DOM), CSRF, SSRF.

Password attacks

  • Brute force, dictionary, credential stuffing, rainbow tables, password spraying.

Attacker mindset — the four-step approach I apply

  1. Identify a target.
  2. Determine how the target can be accessed.
  3. Evaluate attack vectors that can be exploited.
  4. Find the tools and methods of attack.

Then compare to the defender view (the Cyber Kill Chain: reconnaissance → weaponisation → delivery → exploitation → installation → command & control → actions on objectives) and to the MITRE ATT&CK matrix of tactics and techniques.

Threat-modelling methods I’m fluent in

  • STRIDE — Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege.
  • PASTA — Process for Attack Simulation and Threat Analysis; 7 stages (see below).

Risk assessment frameworks

NIST SP 800-30 is the standard I refer to for a formal risk-assessment process — identify, analyse, prioritise, communicate, and periodically re-evaluate risks. Pairs naturally with the NIST RMF for the ongoing management side.

Deliverables I produced

PASTA threat model for a sneaker-marketplace mobile app

Scenario: the growing security team of a sneaker-collector company was about to launch a mobile app for buying and selling shoes. I ran a full PASTA (Process for Attack Simulation and Threat Analysis) threat model across all seven stages.

StageWhat I documented
I. Define business and security objectivesApp allows users to create member profiles; securely processes financial transactions and handles payments, account management, transaction processing. Because it handles payment data, it must comply with PCI DSS.
II. Define the technical scopeAPIs, PKI, AES, SHA-256, SQL. I prioritised APIs because they enable communication with external systems, transmit sensitive info, and are a common cyberattack target — securing them has an outsized impact on overall security and data integrity.
III. Decompose applicationBuilt a data-flow diagram showing how buyer / seller data moves between the app, the payment gateway, and internal storage.
IV. Threat analysisPrioritised threats identified: Injection (SQL injection through the marketplace search / listing forms) and Session hijacking (attackers stealing an authenticated user’s session to impersonate them).
V. Vulnerability analysisTwo exploitable weaknesses: lack of prepared statements (opens SQL injection) and broken API token handling (enables session hijack / impersonation).
VI. Attack modelingBuilt an attack-tree diagram that walked from the weakness through to the impact.
VII. Risk analysis and impactMitigations: enforce SHA-256 for password / credit-card storage; document incident-response procedures; enforce a strong password policy; apply principle of least privilege on APIs and DB access.

Access-control review — contractor still active four years after contract end

Scenario: a login event at 8:29:57 AM on 10/03/23 from IP 152.207.255.255, made by user Robert Taylor Jr with the Legal / Administrator role, accessing payroll systems.

Issue I identified: Robert Taylor Jr was an admin, but his contract had ended in 2019. His account should have been disabled — yet it accessed payroll in 2023.

Recommendations I delivered:

  • Restrict access to sensitive resources based on user roles and job responsibilities.
  • Set user accounts to expire automatically after 30 days or when access is no longer needed.
  • Provide contractors with limited, role-based access only.
  • Enable MFA on all accounts.
  • Regularly audit user privileges to ensure appropriate access levels.

Data-leak analysis — internal folder link accidentally shared publicly

Scenario: a sales manager shared access to a folder of internal-only documents with their team during a meeting. The folder held files for an unannounced product plus customer analytics and promo materials. Access wasn’t revoked afterwards. A sales rep later intended to share the promo link with a business partner on a call, but accidentally shared the internal folder link instead. The partner then posted that link on their company’s social media, assuming it was the promo material.

Framework I applied — NIST CSF hierarchy: Function → Category → Subcategory → Reference. The relevant control was NIST SP 800-53 AC-6 — Least Privilege.

Control (AC-6) — Least Privilege: only the minimal access and authorisation required to complete a task or function should be provided to users.

Control enhancements I recommended:

  • Restrict access to sensitive resources based on user role.
  • Automatically revoke access to information after a defined period.
  • Keep activity logs of provisioned user accounts.
  • Regularly audit user privileges.

Justification I wrote: data breaches are reduced by limiting internal-folder access exclusively to authorised employees and by tying sensitive-resource access to current role. Automatic revocation + activity logging + regular audits give both prevention and accountability.

Parking-lot USB investigation

Scenario: found a USB stick with the hospital logo on the parking-lot ground. No one around had dropped it. Brought it back and investigated it safely.

Safe-handling method: plugged the USB into a virtualisation-software sandbox on an isolated workstation. Virtualisation runs a simulated OS in a container disconnected from other files and networks, so any malware on the USB can’t reach production systems.

Contents I found: personal documents belonging to a person named Jorge, alongside work files containing PII for other individuals and sensitive information about the hospital’s operations. Mixing personal and work files on the same drive is unsafe — it increases the risk of unauthorised access, accidental disclosure and data breach.

Attacker-mindset analysis:

  • Timesheets reveal coworker information usable for targeted phishing / social engineering.
  • Personal info can be used to impersonate trusted contacts and deceive Jorge’s relatives.
  • Employee / schedule / operations details help an attacker gain unauthorised access to business systems or facilities.

Risk analysis: a malicious USB may hold ransomware, spyware, keyloggers, or trojans that infect a computer once connected. If another employee plugged it in, malware could spread across the network; credentials, personal data, business documents and financial records could be exposed and used for identity theft, phishing, or business-disruption.

Recommended mitigations: employee security-awareness training; routine antivirus scans; disable AutoPlay on company computers so malicious code can’t auto-execute on insertion.

Home asset inventory (attacker-mindset self-reflection)

Reflection I wrote:

Attack surfaces of a home — both physical and digital. Physical: doors, windows, garages. Digital: Wi-Fi network, smart-home devices, connected computers. Weak locks, outdated software, poor passwords or an unsecured network all create vulnerabilities that expose the home to unauthorised access or cyber attack.

Attack vectors + defences — unlocked doors and windows, weak Wi-Fi passwords, phishing emails, and vulnerable smart-home devices. Attackers can exploit those to steal personal information, gain unauthorised access, or compromise connected systems. Existing defences include strong locks, alarm systems, firewalls, antivirus, and secure Wi-Fi encryption. Additional protection: enable MFA, keep device software updated, use strong unique passwords, and monitor security cameras and network activity.

Pitfalls I stay aware of

  • Confusing symmetric vs asymmetric encryption — symmetric is fast but key distribution is hard; asymmetric solves distribution but is slow. Real systems combine both (asymmetric to exchange a symmetric session key, then symmetric for the bulk data).
  • Using hashing for confidentiality — hashing is one-way and for integrity only. Don’t “encrypt” sensitive data by hashing it.
  • Skipping the least-privilege step on contractors — the Robert Taylor Jr case above is a classic. Auto-expiry + regular audits are the fix.
  • Plugging in unknown USB sticks on production machines — always sandbox or isolate first.
  • Treating threat modelling as a one-off design exercise — it should be refreshed as the app evolves and new APIs / features change the attack surface.
  • Ignoring the human vulnerability — social engineering exploits people, not technology. Awareness training belongs alongside every technical control.

Additional assets / threats / vulnerabilities concepts I know

Data governance roles

  • Data owner — senior person accountable for the data asset (usually a business leader). Decides classification and who can access.
  • Data controller — the entity that determines the purpose and means of processing personal data (a GDPR term).
  • Data processor — the entity that processes personal data on behalf of the controller (also GDPR).
  • Data custodian — the technical steward who implements the data controls the owner defines.

Data states, restated: at rest (disk / DB — encrypt with AES-256), in transit (TLS / IPsec / SSH), in use (memory protection, confidential computing).

Data exfiltration — unauthorised movement of data out of the organisation; the endpoint many attacks aim for.

Non-repudiation — the guarantee that a party cannot deny having sent / signed something. Enforced by digital signatures + logging + accountability.

Malware types not covered above

  • Scareware — fake “your PC is infected” pop-ups pressuring the user to buy or install something malicious.
  • Dropper — small first-stage program whose job is to download the real payload.
  • Loader — the next stage that loads and executes the payload in memory.

Web-based attack detail

  • Cross-site scripting (XSS) — injecting script into a trusted web page. Three flavours:
    • Reflected XSS — malicious script comes in via a URL parameter and is reflected back in the response (targets one user at a time).
    • Stored XSS — malicious script is saved on the server (e.g. in a comment field) and served to every visitor.
    • DOM-based XSS — script is executed as a result of modifying the DOM in the browser; no server involvement.
  • SQL injection — injecting SQL through an input field; can read, modify or delete the database if inputs aren’t parameterised.
  • Injection attack (general) — feeding untrusted input that the app interprets as code.
  • Input validation — check every input at the boundary; reject anything that doesn’t match the expected shape.
  • Prepared statements — parameterised queries; the fix for SQL injection.
  • Session hijacking — stealing a valid session ID / cookie so the attacker acts as the user without needing the password. Enabled by cookie theft, XSS, weak session-ID generation, MITM.
  • Session ID / Session cookie — token that identifies an authenticated session; must be random, expire, and be transmitted over HTTPS with HttpOnly + Secure flags.
  • API token — equivalent of a session credential for machine-to-machine calls; rotated, scoped, and never checked into source.

More social-engineering variants

  • Angler phishing — impersonating a customer-support account on social media and replying to real users’ complaints with a malicious link.
  • Quid pro quo — attacker offers a benefit (help, gift) in exchange for information or access.
  • Tailgating (piggybacking) — following an authorised person through a secure door before it closes.
  • Rapport — social engineers deliberately build friendly relationships over time to lower a target’s guard.

Cryptography extras

  • Cipher — the algorithm used for encryption (AES, RSA). A cipher plus a mode (e.g. AES-256-GCM) defines the actual transform.
  • Hash function — a one-way function that maps arbitrary input to a fixed-length digest (SHA-256).
  • Hash collision — two different inputs producing the same hash. Rare in strong hashes; possible in broken ones (MD5, SHA-1) — the reason those are deprecated.
  • Salting — adding a unique per-user random value to a password before hashing so two users with the same password get different hashes; defeats rainbow tables.
  • Rainbow table — pre-computed lookup of hash → plaintext for common passwords; effective only against unsalted hashes.

Vulnerabilities & threat operations

  • Zero-day — a vulnerability the vendor doesn’t yet know about, so there’s no patch. Extremely valuable to attackers; usually chained with other techniques.
  • Vulnerability scanner — automated tool that checks systems against a database of known CVEs.
  • Access controls — the overall category of technical + administrative safeguards that enforce authentication and authorisation.
  • Access Control List (ACL) — a list attached to a resource that spells out which principals can do which actions on it.
  • User provisioning / de-provisioning — the lifecycle of creating accounts on hire, adjusting on role change, and revoking on exit; classic point of failure (the contractor-still-active case above).

Broader concepts I’m fluent in that expand on the above

  • Defence in depth — layer controls (perimeter firewall + segmentation + EDR + MFA + monitoring) so no single failure exposes the asset.
  • Zero trust — never trust, always verify; every request authenticated, authorised and encrypted regardless of network location.
  • Adversarial AI — manipulating ML models with poisoned data or crafted inputs to bypass detection.
  • Supply-chain attacks — hitting a trusted third party to reach many downstream targets.
  • Where this ties to my RAN work — the 5G security stack (SUPI/SUCI, 5G-AKA, IPsec, PKI) uses exactly these crypto and IAM primitives; I already reason about identity, authentication and confidentiality at the protocol level.
