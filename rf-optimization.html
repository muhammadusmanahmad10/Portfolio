RF Optimization & Performance Tuning

Optimization is the continuous loop of measure → diagnose → adjust → verify that keeps a live network performing as traffic and interference change. Across 2G–5G I tuned coverage, capacity and mobility by adjusting radio parameters and validating the result against KPIs — turning degradations into corrective actions, not guesswork.

How I run an optimization / audit

I monitor RAN KPIs and counters to spot degradations, then run a network audit to find the root cause — frequently a misconfiguration (wrong tilt/azimuth, missing neighbour relation, incorrect power, overshooting cell, or an interference source). I apply the corrective change and then re-measure to confirm the KPI actually improved, closing the loop rather than assuming the fix worked.

  • Interference analysis — identify external/internal interference and uplink noise rise degrading SINR and throughput.
  • Coverage tuning — tilt/azimuth/power changes to balance coverage vs overshoot and reduce inter-cell interference.
  • Capacity actions — load balancing across carriers/layers, adding carriers, enabling CA where the device/cell supports it.
  • Mobility tuning — handover parameter adjustment to cut call drops and ping-pong while preserving service continuity.
  • Audit-driven corrections — systematically resolve config deviations found in health checks.

Case — RSSI unbalanced / RTWP too low

Symptom
Repeated KPI alarms flagging "RSSI unbalanced" on LTE / NR cells, and on some sectors "RTWP too low" — UL noise floor dropping well below the expected ~−105 dBm thermal-plus-noise-figure level on one branch while the other branch sat in the normal band.
What it usually means
A branch imbalance is either internal (faulty RX path: TMA / jumper / RRU port / feeder / connector water-ingress) or external. RTWP too low almost always points to a broken / disconnected RX path; RTWP too high points to interference.
How I troubleshoot it
  1. Online FFT scan on the LMT — sample the UL spectrum live, per branch, with the cell active. A broadband elevated noise floor or a clean carrier in-band means external interference; a flat / dead spectrum on one branch with the other one healthy points to an internal RX failure.
  2. Offline FFT scan — block / disable the cell’s own transmission and re-scan. If the in-band signature persists with the cell off, it's external (PIM from another operator, a repeater, illegal emitter); if it disappears, it's self-generated / internal PIM.
  3. Branch swap / loopback — if FFT points internal, swap RF jumpers between branches and re-check which branch the imbalance follows: the RRU port, the feeder, or the antenna element.
Typical fixes
Re-torque / replace a water-ingressed connector, swap a failing TMA / RRU port, replace a faulty jumper, or escalate an external-interference case to the spectrum / regulatory team with the captured FFT trace as evidence.

Takeaway: the online vs offline FFT pair is the cleanest way to split internal vs external before swapping any hardware — it saves a truck roll when the real fault is a neighbour’s emitter, and it pinpoints the failing component when it's genuinely a faulty RX path.

Case — femto rebooting after neighbour-relation table overflow (partial entries counted toward capacity)

Symptom
The femto was repeatedly rebooting when its neighbour-relation table grew large. The reboots correlated with batches of ANR / manual neighbour-relation additions during integration of nearby macros.
Investigation
The vendor’s neighbour-relation table has a maximum capacity (commonly in the order of 256 entries per cell on this platform — exact value depends on the build / configuration). I expected the platform to count only fully-formed neighbour relations (with valid PCI + TAC + frequency) against that limit. The trace showed something different: partial / duplicate neighbour entries — ones where PCI or TAC were missing (showing as N/A) — were still being added and were still occupying slots in the table. ANR was inserting a new entry every time the femto saw an SSB from a neighbour, and because the duplicate-detect logic keyed on full identity (PCI + TAC), entries with N/A fields didn’t dedup against the “complete” copy of the same neighbour. The table filled with a mix of real entries and partial duplicates of the same physical neighbour.
Root cause
The neighbour-relation table’s capacity accounting didn’t distinguish complete entries from partial ones — both consumed a slot. Under heavy ANR activity the count crossed the configured maximum, the platform hit an internal-resource exception, and the femto rebooted to recover.
Fix
Two parts. Operational: pruned the table by clearing partial / N/A neighbour relations and re-tightening ANR so only complete observations (PCI + TAC + frequency present) were committed. Configuration: raised the cell’s neighbour-relation cap to the platform’s allowed maximum after confirming the headroom on memory / processing didn’t introduce new risk. After the prune + cap change, ANR additions stayed inside the limit and the femto stopped flapping.
Concept & takeaway
Neighbour-relation tables are bounded; not every entry that consumes a slot is a useful neighbour. When a femto reboots under heavy ANR activity, check whether partial / duplicate entries are eating slots before raising the cap. Takeaway: “table-full” reboots are usually a count-vs-quality problem, not a raw-capacity problem.

Field notes & common pitfalls

  • Always verify after changing. An adjustment that "should" help can shift the problem to a neighbour — re-measure.
  • Good RSRP ≠ good quality. SINR and interference often matter more than raw signal strength.
  • Mobility is a balance. Over-aggressive handover cuts drops but creates ping-pong and signalling load.
  • Audit first. Most degradations are misconfigurations, not capacity — find the deviation before adding hardware.
