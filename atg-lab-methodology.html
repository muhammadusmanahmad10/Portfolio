ATG Lab Validation Methodology

Every new ATG ground-station (GBSS) software load and every new aircard firmware load passes through the lab before it’s flown. The lab is the gate between the vendor’s release and the live network — so the lab plan has to cover the three things that will decide whether the load survives on a real flight: call setup, TCP/UDP throughput, and handover. This page captures the methodology I use to make the lab a credible proxy for the air.

What gets validated per load

  • GBSS software load — the ground base-station software. Changes can affect scheduler, mobility, PRACH handling, OAM counters, and interactions with the aircard.
  • Aircard firmware load — the aircraft-side LTE modem firmware. Changes can affect measurement reporting, link adaptation behaviour, PRACH preamble selection and power control.
  • Every new load of either kind passes the same lab plan before field release.

The three canonical lab surfaces

1. Call setup

  • Initial attach — from power-on to RRC_CONNECTED + default bearer.
  • Reconnection after RLF — re-establishment via T311.
  • Tracking Area Update, Paging-response, Idle-to-Connected.
  • Pass/fail on setup time, setup failure, and MAC-RA count during the run.

2. Throughput (TCP & UDP, DL & UL)

  • UDP at target rates — proves radio can carry; isolates from transport.
  • TCP single-stream — the user-visible case; must be qualified against BDP.
  • TCP parallel streams — confirms air-interface capacity when single-stream is BDP-bound.
  • Pass/fail on throughput floor and ceiling, BLER, scheduler fairness across multiple UEs.
  • See Radio-Transport Boundary for how we decide the test is actually measuring the radio.

3. Handover

  • Intra-eNB and inter-eNB HO in both directions.
  • HO under interference injection via Spirent / Vertex (RoT moderate & heavy).
  • HO under channel emulation that mimics aircraft banking fades.
  • Pass/fail on HO success %, HO interrupt time, re-establishment-failure on failed HO.
  • Mobility parameters (TTT, hysteresis) swept where applicable to confirm the load behaves across the operator’s range — see High-Mobility Handover Tuning.

Making the lab a credible proxy for the air

  • Channel emulation — Spirent / Vertex reproduce long-delay propagation (100 km round trip), aircraft-speed Doppler, and interference from co-channel neighbours.
  • PRACH config — use the actual field PRACH parameters (format 3, large Ncs, HighSpeedFlag on). See PRACH for ATG.
  • PCI collision cases — deliberately set two emulated cells to mod-3 conflict to validate behaviour — see PCI Planning.
  • RoT discipline — verified via UL RSSI counter on the eNB; a test case is only meaningful if the injected interference actually landed (Lab Interference & RoT).

Test-case discipline — pass/fail must be reproducible

  • Each test case documents: pre-conditions, exact configuration, execution steps, measurements collected, and pass/fail criteria.
  • Pass/fail criteria are numeric and unambiguous — e.g. “HO success rate ≥ 99.5% over 100 attempts, interrupt time ≤ 150 ms 95th-percentile.”
  • Every pass/fail decision is backed by a log capture that another engineer can re-analyse.

Gate-to-flight checklist

  1. All P0 test cases passed.
  2. All P1 test cases passed or waived with vendor sign-off.
  3. Any P2 open items tracked in Vendor Defect Tracking.
  4. Baseline KPIs from the previous load captured for comparison.
  5. Load-note written: what changed, what we tested, what we expect on the flight.

Pitfalls I stay aware of

  • Lab-only “good enough” — a load that passes benign lab conditions can still break under aircraft Doppler. Always include Doppler + long-RTT emulation.
  • Pass/fail that depends on opinion — numeric criteria only, documented up front.
  • Skipping the baseline comparison — without last-load numbers, a regression can hide in plain sight.
