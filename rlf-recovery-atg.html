RLF & Recovery on ATG — Cause Codes

Not every radio-link failure is the same. On ATG I separate RLFs by the cause code that ended the RRC connection — T310 (DL out-of-sync), RLC max-ReTx (UL data unrecoverable), MAC-RA (UL access broken) — because each one points at a different part of the network and a different fix. Recovery is governed by T311; a re-establishment that doesn’t complete before T311 expiry forces a full connection setup, which breaks the user session visibly.

T310 (DL out-of-sync) RLC max-ReTx (UL data) MAC-RA (UL access) T311 re-establishment SIB-acquisition failure

The three RLF causes — what they mean

Cause codeWhere it firesWhat’s actually broken
T310 expiry UE DL side (physical-layer problem indications accumulate) UE can no longer decode the serving cell reliably — DL out-of-sync. Typical of coverage/fade or a mod-3-conflicted neighbour corrupting CRS.
RLC max-ReTx UE UL (data-plane AM RLC) A UL RLC PDU can’t be acknowledged even after maxRetxThreshold retransmissions. The UL path has died while a UL data session is in progress.
MAC-RA failure UE MAC during random access The UE tried to re-establish contact with the cell via PRACH and failed to complete random access within the configured attempts. Points at PRACH config or UL geometry.

Recovery flow — T311 is the stopwatch

  1. RLF fires — one of T310 / RLC max-ReTx / MAC-RA ends the current RRC connection.
  2. UE starts T311 and begins a cell-search for a suitable candidate.
  3. If the UE finds a cell and reads its SIBs, it issues RRCReestablishmentRequest (Msg3 on PRACH).
  4. If the eNB has the UE’s context, it responds with RRCReestablishment.
  5. UE sends RRCReestablishmentComplete; session resumes with cause code logged.

If T311 expires before step 4 lands, the UE drops to RRC_IDLE and must do a full connection setup (and NAS re-attach on EPS) — which is visible to the user.

Why re-establishment often fails on ATG

  • No dominance at cell-edge. If the UE is in a no-dominance zone when RLF fires, every candidate cell has similar RSRP and SINR — no cell is “strong enough” to complete random access reliably.
  • SIB-acquisition failure on the candidate cell — usually because the target is mod-3-conflicted with the serving cell (PCI Planning) and SIB decoding fails.
  • Msg3 PRACH failure — UE’s PRACH preamble doesn’t reach / isn’t detected on the candidate cell. See UL Random Access & PRACH for ATG.
  • eNB no longer has context — the UE context was freed; eNB answers with reject and UE falls back to full setup.

Reading the RLF story in a flight log

  1. Mark the RLF timestamp.
  2. Walk back 10–15 s on the SINR and MCS trace. What was the trajectory?
  3. Was there an A3 trigger that failed to complete? If yes, check TTT and hysteresis.
  4. Check the cause code — T310 vs RLC vs MAC-RA tells you which part of the chain actually died.
  5. Walk forward: did T311 catch the recovery, or did the UE drop to full setup?
  6. Overlay attitude (bank angle) — is this a geometry event or a network event?

Mitigations and where each attaches

Observed patternTypical fix
T310 cluster during banking / cell-edgeShorten TTT, add hysteresis — see High-Mobility Handover Tuning.
RLC max-ReTx during UL uploadCheck UL SINR, UL power headroom, scheduler aggression on UL in low-headroom.
MAC-RA during recoveryCheck PRACH format / Ncs / cell-radius / high-speed set — see PRACH for ATG.
Re-establishment failing with SIB-acquisition fail on targetCheck target cell PCI mod-3 vs serving — see PCI Planning.
No-dominance coverage holeTilt / power to establish cell dominance; mod-3 re-plan.

Pitfalls I stay aware of

  • Lumping all RLFs together. Cause code is the diagnostic key.
  • Chasing a T310 cluster as a mobility bug when it’s actually a PCI mod-3 collision on the serving cell.
  • Chasing an RLC max-ReTx as a UL-radio problem when it’s a UL scheduler keeping MCS too high in low-headroom.
  • Missing the T311 expiry — counting re-establishment-failure and full-setup-fallback separately matters for the user-impact story.
