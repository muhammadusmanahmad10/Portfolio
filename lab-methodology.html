Lab Validation Methodology

Good validation isn't just running test cases — it's knowing what kind of testing you're doing, picking the right device for the feature, and choosing the right tool for the load. This page covers the methodology that frames my hands-on lab work: conformance vs operator acceptance, UE-category selection, and the simulator/traffic toolchain.

Conformance vs operator acceptance testing

3GPP ConformanceOperator Acceptance
Question"Does it meet the global spec?""Does it work in our network?"
WhereAccredited labs (GCF/PTCRB)Operator labs
ScopeProtocol (RRC/NAS/SIP), RF (power, spectrum mask), mobilityFunctional (attach, VoNR, HO, CA/EN-DC), stability/soak, interop with operator IMS/5GC/OSS
NatureStrict pass/fail vs 3GPPReal-world scenarios, operator-specific features & KPIs

My work is operator acceptance — validating that a product is deployment-ready in the operator's specific environment (band combinations, APN/DNN profiles, emergency-call handling, operator KPIs). Conformance proves standards compliance; acceptance proves it's safe to launch.

Choosing the right UE for the feature

Feature under testUE requirement
Basic attach / dataAny capable UE
Carrier AggregationLTE Cat 6+ (Cat 12+ for 256-QAM throughput)
EN-DC5G NSA-capable device
VoNR5G SA-capable device
💡Critical discipline: if the wrong UE category is used, the feature won't appear even when the network supports it — the limitation is the device, not the cell. I keep a device matrix and band-lock UEs so I never mistake a handset limit for a network fault. (This is exactly why the BWPS / device-attach issues needed careful network-vs-device isolation.)

The toolchain

Hands-on

  • TM500 — load/stress UE emulation for multi-UE attach, mobility and throughput.
  • IXIA — backhaul traffic generation & policing (the 100 Mbps policer setup).
  • iPerf / Ookla / pingtools — TCP/UDP/HTTP throughput & latency.
  • Wireshark / tshark / XCAL5 — packet & SIP trace analysis.

Familiar (industry simulators)

  • Spirent / Keysight — large-scale UE emulation, traffic generation and mobility simulation used in lab validation; emulate hundreds/thousands of UEs for repeatable, scalable stress tests and controlled failure scenarios.
  • I understand their role and outputs (KPIs, protocol logs, pass/fail reports) and can apply my existing test-flow and KPI knowledge to them directly.

Note: TM500/IXIA/Wireshark/XCAL5 are hands-on; Spirent/Keysight are listed as industry-standard tools I'm familiar with, presented honestly as knowledge rather than primary hands-on experience.

Soak / stability testing

Functional tests prove a feature works for ten minutes; soak testing proves it survives 8–24–72 hours under sustained load. I run continuous attach/data/VoNR traffic and watch CPU, memory and disk trends (for memory leaks), alarm/error counters, and KPI stability (attach success, drop rate, throughput) — because a cell that crashes after six hours from a memory leak is not deployment-ready, even if it passed every functional test. Field notes

  • Name the test type. Conformance and acceptance answer different questions; don't conflate them.
  • Match the UE to the feature before declaring a network defect.
  • Pick the tool for the question — controlled (iPerf/Spirent) vs real-world (Ookla) give different numbers.
