Lab Validation Methodology

Good validation isn't just running test cases — it's knowing what kind of testing you're doing, picking the right device for the feature, and choosing the right tool for the load. This page covers the methodology that frames my hands-on lab work: conformance vs operator acceptance, UE-category selection, and the simulator/traffic toolchain.

Conformance vs operator acceptance testing

Question"Does it meet the global spec?""Does it work in our network?"

My work is operator acceptance — validating that a product is deployment-ready in the operator's specific environment (band combinations, APN/DNN profiles, emergency-call handling, operator KPIs). Conformance proves standards compliance; acceptance proves it's safe to launch.

💡Critical discipline: if the wrong UE category is used, the feature won't appear even when the network supports it — the limitation is the device, not the cell. I keep a device matrix and band-lock UEs so I never mistake a handset limit for a network fault. (This is exactly why the BWPS / device-attach issues needed careful network-vs-device isolation.)

The toolchain

Hands-on

  • TM500 — load/stress UE emulation for multi-UE attach, mobility and throughput.
  • IXIA — backhaul traffic generation & policing (the 100 Mbps policer setup).
  • iPerf / Ookla / pingtools — TCP/UDP/HTTP throughput & latency.
  • Wireshark / tshark / XCAL5 — packet & SIP trace analysis.

Test-case execution discipline

For every test case I cover three things up front, before the test is ever run, so the result is unambiguous and reproducible:

  • What do we need to check in this test case — the precise behaviour, parameter, or KPI the test is validating (e.g. RRC setup success, the right 5QI on the QoS flow, Z-axis present in the location object, BLER below the target).
  • Method to execute the test case — the step-by-step recipe: pre-conditions, UE configuration, traffic pattern, tools to drive it (TM500 / iPerf / Ookla / XCAL5 / Wireshark), and what logs to capture.
  • Pass / fail criteria — the exact, measurable rule that decides the result (numeric KPI threshold, presence/absence of a signalling message, log evidence). No subjective “it looks fine.”

This is what I packaged into the Basic Sanity Test Guide — for each test case in each category, the objective, execution steps, and pass/fail criteria are documented once so the next engineer running it gets a consistent result.

Soak / stability testing

Functional tests prove a feature works for ten minutes; soak testing proves it survives 8–24–72 hours under sustained load. I run continuous attach/data/VoNR traffic and watch CPU trends, alarm/error counters, and KPI stability (attach success, drop rate, throughput) — because a cell that crashes after six hours is not deployment-ready, even if it passed every functional test. Field notes

  • Name the test type. Conformance and acceptance answer different questions; don't conflate them.
  • Match the UE to the feature before declaring a network defect.
  • Pick the tool for the question — controlled (iPerf) vs real-world (Ookla) give different numbers.
