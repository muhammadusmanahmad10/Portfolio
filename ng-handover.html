NG (N2) Handover & AMF Selection

When there is no Xn interface between source and target gNB, or the target sits under a different AMF, 5G SA uses an NG (N2) handover: the source gNB asks the AMF to coordinate the prepare phase via NGAP. The AMF talks to the target gNB, relays the handover command back, and re-points the user plane — so the core is in the path for the whole preparation, unlike Xn.

3GPP TS 38.413 (NGAP) 3GPP TS 23.502 §4.9.1 3GPP TS 29.518 (AMF svc) Validated on a live 5G SA Femto deployment (band n41)

Case study — UE can't attach: AMF relative-capacity in an AMF pool

Symptom
UE failed to attach via the femto. The gNB kept assigning the UE to one specific AMF in the pool, and that AMF was unresponsive — the UE was not moved to a healthy AMF.
Investigation
The AMF pool had 20 AMFs: 11 with relative AMF capacity = 50 and 9 with capacity = 1. The gNB performs weighted AMF selection based on relative AMF capacity advertised in NGAP. Traces showed the gNB selecting a high-weight AMF that was itself unreachable; the security gateway confirmed it was unreachable from their side too.
Root cause
The unreachable AMF was still advertising a high relative-capacity weight, so the gNB kept steering UEs to it instead of failing over to a healthy AMF. Stale/incorrect capacity weighting + no effective failover for that node.
Fix & outcome
Escalated with traces to the core team, who restored AMF reachability; attach recovered. I also verified the boundary behaviour: when all AMFs in the set advertise ARC = 0 and the affected node is unreachable, the femto goes out of service and no UE attaches. (If an AMF is reachable, UEs can still attach via that node even with ARC=0 advertised — the AMF must be both deprioritized and unreachable to fully take it out of the pool.)

Takeaway: attach failures aren't always RAN — AMF selection weights and core reachability decide which node a gNB trusts. Reading the relative AMF capacity IE turns a vague "UE won't attach" into a precise core escalation.

A second attach failure I isolated

A separate attach failure traced to an unstable / newly-introduced AMF that was not yet reachable. Rather than guessing, I correlated the NAS/NGAP rejection with the security gateway's confirmation that the node was unreachable end-to-end, then handed a clean, evidence-backed escalation to the core team. Fixed at the core; attach restored. The discipline here — prove unreachability with signalling before escalating — is what keeps multi-team debugging fast.

Field notes & common pitfalls

  • Wrong interface chosen. If both gNBs share an AMF and Xn is up, the network should use Xn — seeing NG used instead can point to a missing/inactive Xn link.
  • AMF selection is weight-driven. A high relative-capacity weight on an unhealthy node silently black-holes attaches; check the capacity IE before blaming the RAN.
  • ARC = 0 everywhere + AMFs unreachable ⇒ out of service. If any AMF is still up, UE attach can still succeed; the AMF must be both deprioritized and unreachable to disappear from the pool.
  • Inter-AMF adds relocation. Across AMFs there's a forward-relocation step between AMFs that you won't see in the intra-AMF case.
