Vendor Escalation & Defect Tracking

New loads ship with new defects. Flight-test and lab exposure both generate them. The job of the ATE engineer is to catch the defect with evidence, escalate it to the vendor with everything they need to reproduce, and track it across loads until it’s fixed and validated. The quality of a vendor defect submission is what determines whether the next load fixes the problem or carries it forward another cycle.

Anatomy of a vendor defect I submit

  • Title — one sentence, names the observed behaviour and the condition.
  • Build / load IDs — GBSS software version, aircard firmware version, exact test-bed config.
  • Reproducer — step-by-step lab procedure, documented so another engineer can run it unchanged.
  • Observed vs expected — what the trace actually shows, what the spec / previous load produced.
  • Evidence — log captures (eNB side + aircard side + Wireshark), KPI snapshots, MATLAB plots with the event marked.
  • Impact — which KPIs this moves, what user experience looks like.
  • Suspected root cause — if I have a theory, I say so. Clear about what’s diagnostic vs what’s speculative.
  • Workaround — if any; parameter change that masks it; operational mitigation.

Diagnosed / recommended / validated — wording discipline

These three words describe different ownership:

  • Diagnosed — I found what’s broken (e.g. scheduler keeping MCS too high in low-headroom). I did not change the vendor’s code.
  • Recommended — I proposed a parameter change or an algorithm change (e.g. TTT 320 ms → 80 ms).
  • Validated — I verified a change (vendor fix or a recommended parameter change) produced the expected outcome on subsequent loads or flights.

I keep this wording explicit in every defect and every write-up so there’s no implication that I own vendor code I don’t own.

Reproducer design — what makes a defect “actionable”

  • Deterministic. Same inputs → same output. Flaky reproducers get deprioritised and die in the queue.
  • Lab-runnable if possible. A flight-only reproducer takes weeks; a lab reproducer takes an hour. Where I can emulate the field condition (via Spirent / Vertex channel emulator), I always provide the lab setup.
  • Minimal. Strip to the smallest sequence that still shows the behaviour.
  • Instrumented. The reproducer includes the exact log channels and counter captures the vendor will want.

Cross-load tracking

  • Every open defect carries a vendor ID and a local ID across loads.
  • Per new load, I re-run the regression set that contains the open defect’s reproducer. Three outcomes:
    • Fixed: close with fix-validation note.
    • Partially improved: keep open, update severity, re-run next load.
    • Unchanged: keep open, follow up with vendor; if it ages past N loads, escalate severity.
  • The vendor defect list is reviewed per load and reported alongside the executive flight summary — see Flight KPI & Executive Reporting.

Fix validation — what “done” actually means

  • A vendor fix is not “done” because the vendor says so. It’s done when the reproducer no longer produces the behaviour, and no regression appears in the surrounding test cases.
  • Fix-validation evidence is log captures of the same reproducer on the new load, with the previous behaviour visibly absent.
  • I write the validation note explicitly so the defect record stays useful as institutional knowledge (“fixed in load X.Y.Z by a change to the OLLA target per codeword; validated via reproducer L-123 showing BLER returns to target after 1.5 s”).

Pitfalls I stay aware of

  • Submitting a defect without a reproducer. It will sit in the queue.
  • Claiming “fixed” based on absence of the symptom on one flight. One flight isn’t a regression test. Re-run the reproducer.
  • Using “owned” language on code I didn’t write. Diagnosed / recommended / validated are the honest verbs.
  • Losing track of aged open items. Every load reviews the full open list, not just new findings.
