Troubleshooting · Published Case Studies

RAN Troubleshooting Case Library

During large-scale multi-RAT integration I documented real field faults — symptom, investigation, root cause, and resolution — and published them on the equipment vendor's official engineering case portal (ICase) so other engineers could resolve the same issue faster. Below is a representative selection. Each is a genuine site incident I diagnosed and closed, organised by failure domain.

17+ published cases 2G / 3G / 4G / 5G NSA Integration · Hardware · Software · Transport

Integration & configuration conflicts

A1
Inter-system control-rights conflict after NSA 5G integration on an existing BBU Adding 5G NSA to a live baseband triggered a control-rights conflict between technologies sharing the BBU. Resolved by correcting the inter-system control/working-mode ownership so legacy and NSA could coexist.
A2
RRU topology/config mismatch alarm — working-mode extension same as peer end An eNodeB raised a topology/config-mismatch alarm because the RF unit's working-mode extension matched the peer end when it shouldn't. Aligning the working-mode config to the peer cleared it.
A3
Inter-system RF-unit parameter conflict — wrong RF working mode at GU end Conflict alarms from an incorrect RF-unit working mode on the GSM/UMTS (GU) end. Corrected the RF working-mode parameters to the intended per-technology split.
A4
Inter-system site-level configuration conflict on eNodeB Site-level config conflict, again from a working-mode extension matching the peer end — resolved by realigning the per-system configuration.
A5
RAT conflict between separate MPT alarms after new LTE site integration New LTE integration produced RAT-conflict alarms across MPT main processing units. Root-caused to a multi-RAT resource/working-mode clash and corrected in the site script.
A6
GU site went to mediation after new L700 integration as non-SDR Integrating L700 as a non-SDR config pushed the GU site into mediation. Resolved by correcting the SDR/non-SDR configuration for the band.

RF & cell-setup failures

B1
U900 cell setup failed — frequency overlapped in G900 MAGROUP The U900 cell wouldn't set up because its frequency overlapped a frequency already in the G900 MA-group. Re-planned the frequency allocation to remove the overlap.
B2
U900 cell setup failed — FREQBWH of hardware not OK Cell setup failed due to a hardware frequency-bandwidth (FREQBWH) capability mismatch. Identified the hardware/config limitation and aligned the carrier configuration accordingly.
B3
G900 RRU not coming up in a CPRI MUX scenario In a CPRI MUX (multiplexed fronthaul) topology the G900 RRU failed to come up. Traced to the CPRI mux chain/topology configuration and corrected the port/working-mode mapping.
B4
Local-cell capability decline — some RRUs in the IDBS cell not usable A NodeB reported reduced local-cell capability because some RRUs in the indoor (IDBS) cell were flagged unusable. Restored the RRU usability/config to recover full cell capability.

Hardware & board faults

C1
Cells-unavailable alarm due to faulty UBBP A faulty baseband processing board (UBBP) took cells out of service. Isolated the board as the fault and drove its replacement/recovery to restore the cells.
C2
External-alarm reference problem across all technologies due to a GTMU issue External-alarm references were wrong across all RATs because of a GTMU (main control/timing/transmission unit) issue — a single shared-unit fault with multi-technology symptoms.
C3
Burglar & water external alarms misreporting on 2G after EMU installation After an environment-monitoring unit (EMU) install, external (burglar/water) alarms misreported on 2G. Corrected the EMU external-alarm port mapping/config.

Software, upgrade & transport / security

D1
S1 interface alarm after migrating to a third-party PKI server Migrating to a third-party PKI server broke the S1 interface (certificate/IPsec trust path). Re-established the security/certificate configuration so S1 recovered — an early parallel to the 5G IPsec/cert work I do now.
D2
Software-package download failed — incorrect FTP parameter settings Package download failed due to wrong FTP parameters. Corrected the FTP server/credentials/path settings to complete the download.
D3
Board software-synchronisation alarms — software not supplementing on a board Sync alarms because software wasn't supplementing onto a particular board. Re-ran the targeted software synchronisation to that board.
D4
LMT limited-packages issue after software upgrade Post-upgrade, the local maintenance terminal showed a limited-packages state. Restored the correct package/license set so full LMT functionality returned.

Why this matters

Publishing these cases did two things: it closed real outages across thousands of integration sites, and it turned each fix into reusable knowledge for the wider engineering community. The throughline to my current 5G SA work is the same diagnostic method — separate symptom from cause, prove the root cause with logs/alarms before acting, and document it so the next engineer is faster.
