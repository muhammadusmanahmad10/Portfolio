Flight KPI & Executive Reporting

Every flight ends with a per-flight executive summary shared with Gogo and vendor stakeholders. The job of the summary is not to show data — it’s to answer four questions: was the user experience good, where did it break, why, and what fixes are proposed. The KPI set and the report structure below are what I use to make that explicit, comparable across flights, and fast to act on.

Connected-time % Available-time % HO-failure % RLF counts by cause DL / UL throughput

The KPI set

KPIDefinitionWhy it matters
Connected-time %Time in RRC_CONNECTED / total flight time.The “was the service there” headline.
Available-time %Connected + data plane up / total flight time.Not all connected time is usable; this is what the user actually sees.
Handover-failure %Failed HO / total HO attempts.Mobility health — the core ATG risk area.
Connection-setup-failure %Failed initial / re-attach setups.Captures the dropouts that break sessions visibly.
Avg / Max DL throughputAggregated over flight.The user-visible speed; max captures best-case radio behaviour.
Avg / Max UL throughputAs above, uplink.Narrow-UL ATG has UL as the bottleneck for many apps.
RLF totalCount.Headline fault count.
RLF by causeT310 / RLC-maxReTx / MAC-RA splits.Points at which part of the chain broke.
Re-establishment-failure countCount.Captures the dropouts the user actually experienced.

The report structure

  1. Executive summary — 3 bullets: was it good, where did it break, what’s the ask.
  2. KPI table — the full set above, with the previous flight’s numbers alongside for comparability.
  3. Key findings — 3–6 bullets with named root causes (e.g. “3 RLFs clustered in the KBOS–KJFK bank-angle region, T310 cause — PCI mod-3 conflict pair 12 / 15”).
  4. Plot pack reference — link to the MATLAB-generated PDF plot pack for engineers.
  5. Recommended actions — concrete, owner-named: “Gogo RF team: PCI re-plan sector 12 to mod-3 ≠ 15”, “Vendor: schedule-side investigation on CQI recovery lag after HO”.
  6. Open items from previous flights — defect IDs, status, next check.

Making it comparable across flights

  • Same KPI set every flight, same formula.
  • Same plot pack layout.
  • KPIs reported alongside the previous flight’s numbers for trend.
  • Defect IDs carry forward until closed — see Vendor Escalation & Defect Tracking.

Audience discipline

  • Executive readers — need the 3-bullet summary and the KPI deltas, not the plots.
  • Engineering readers — need the plot pack and the specific message-level evidence.
  • Vendor teams — need the defect ID, the trace reference, and the proposed reproducer.
  • One report, three audiences — which is why the structure above is layered.
