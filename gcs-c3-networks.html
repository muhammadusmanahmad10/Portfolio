Networks and Network Security

How I think about the network from a security angle — the devices that carry the traffic, the protocols that ride on them, the attacks that exploit both, and the hardening that closes them down. My RAN background covers most of this stack already (SCTP, IPsec, TCP/UDP, DNS, DHCP, packet captures) — this page is how I frame that knowledge, plus the real investigations and reports I produced during the certificate.

Network architecture

Devices that carry the traffic

  • Hub — repeater; forwards every frame to every port. Rare in modern networks.
  • Switch — L2 device; learns MAC addresses and forwards frames only to the destination port.
  • Router — L3 device; forwards packets based on IP address; connects different networks.
  • Modem — converts between the internal network and a WAN link (cable / DSL / fibre / cellular).
  • Firewall — enforces which traffic can enter or leave a security zone; stateful, stateless or next-gen (NGFW).
  • Load balancer — distributes incoming requests across multiple backend servers to keep them from being overloaded.

Network types

  • LAN — local network (office, home).
  • WAN — wide-area network (branches connected together).
  • WLAN — wireless LAN (Wi-Fi).
  • VPN — encrypted tunnel over an untrusted network so remote workers can safely reach the corporate network.
  • Cloud network — resources hosted by a cloud provider (AWS / GCP / Azure) and reached over the internet.

TCP/IP stack, mapped to OSI

  • Network access ↔ OSI L1/L2 (physical + data link). Frames, MAC, Ethernet.
  • Internet ↔ OSI L3 (network). IP, ICMP, ARP; routing.
  • Transport ↔ OSI L4. TCP (reliable, connection-oriented) and UDP (unreliable, connection-less).
  • Application ↔ OSI L5–L7 (session + presentation + application). HTTP / HTTPS, DNS, DHCP, SSH, SMTP, FTP.

IPv4 vs IPv6 and RFC 1918 private ranges (10.x.x.x, 172.16–31.x, 192.168.x) are the everyday address vocabulary. MAC vs IP — MAC is the burnt-in L2 identity, IP is the routable L3 identity assigned per network.

Protocols and where they live

  • TCP — connection-oriented, reliable, ordered; the three-way handshake is SYN → SYN-ACK → ACK. The server allocates memory and a connection-table slot on SYN-ACK, so half-open connections are expensive.
  • UDP — connection-less, unreliable, fast; used for DNS, DHCP, voice, video.
  • ARP — resolves IP → MAC on the local subnet; abused by ARP poisoning.
  • ICMP — control / diagnostic (ping, traceroute, "destination unreachable"); abused by ICMP flood, Smurf attack.
  • HTTP (80) / HTTPS (443) — the web; HTTPS = HTTP over TLS.
  • DNS (53) — name → IP; abused by DNS poisoning, cache poisoning, DNS tunneling.
  • DHCP (67/68) — dynamic IP allocation; abused by rogue DHCP servers.
  • SSH (22) — secure remote shell; replacement for the deprecated Telnet (23).
  • FTP / SFTP — file transfer; SFTP is over SSH.
  • SMTP / IMAP / POP3 — email transport.
  • 802.11 Wi-Fi — WPA2 vs WPA3 (WPA3 adds forward secrecy and a stronger handshake).

Why this ties into my RAN background: the 5G RAN transport stack — NGAP over SCTP over IP, GTP-U over UDP, IPsec / IKEv2 for the security gateway, PTP over UDP or Ethernet for sync — is the same protocol vocabulary a SOC analyst reads on the wire.

How attackers hit the network

Passive vs active attacks

Passive = sniffing / reconnaissance; the attacker observes but doesn’t modify traffic. Active = injection, spoofing, tampering.

Denial of Service (DoS) and Distributed DoS (DDoS)

  • SYN flood — attacker fires many TCP SYNs; server holds memory for each half-open session; legitimate connections can’t get in.
  • ICMP flood — overwhelm the target with ping traffic.
  • Smurf attack — spoofed broadcast ICMP amplification (older).
  • Amplification / reflection — abuse DNS or NTP to multiply traffic against a victim.

Spoofing and interception

  • IP spoofing — forge the source IP.
  • MAC spoofing — forge the source MAC.
  • ARP poisoning — associate the attacker’s MAC with a victim’s IP on the LAN.
  • DNS poisoning — feed the resolver a wrong IP for a domain so victims connect to the attacker’s server.
  • On-path attack (MITM) — attacker sits between two endpoints, intercepts and can modify traffic.
  • Replay attack — capture then re-transmit valid traffic to gain access.
  • Malicious packets — fragmented or crafted headers designed to evade an IDS or crash a stack.

Network and system hardening

Network hardening

  • Patch management and secure device configuration.
  • Disable unused services and ports; port filtering.
  • ACLs and network segmentation so a compromise in one segment doesn’t spread to the whole network.
  • DMZ for internet-facing services; jump hosts for admin access.
  • Firewall rulesets reviewed on a regular cadence; deny by default, allow by exception.
  • IDS / IPS to detect (IDS) or automatically block (IPS) suspicious traffic.

OS hardening

  • Baseline / gold-image configuration; endpoint patching cadence.
  • Host firewall + endpoint EDR / AV.
  • MFA everywhere for admin and remote access.
  • Principle of least privilege on both accounts and services.
  • Password policy: length, character set, no reuse, lockout after N failed attempts, rotation cadence.

Firewalls, VPNs and modern design

  • Firewall types — stateless (per-packet ACL) vs stateful (tracks connections) vs NGFW (adds application awareness, IPS, TLS inspection).
  • VPN — encrypted tunnel using IPsec (site-to-site or remote-access) or TLS; encapsulates the inner IP and encrypts it.
  • Cloud shared-responsibility model — provider secures the fabric, customer secures configuration, data and IAM. Hybrid multiplies the attack surface.
  • Zero trust — never trust, always verify; every request is authenticated, authorised and encrypted regardless of network location.
  • Defence in depth — layered controls so a single failure never exposes the asset.

Deliverables I produced

Cybersecurity Incident Report — network traffic analysis (DNS unreachable)

Scenario: customers reported “destination port unreachable” when trying to reach yummyrecipesforme.com at 1:24 pm. I ran a tcpdump packet capture and analysed the log.

What I saw in the log: the browser issued a UDP DNS query to the DNS server on port 53 (query ID 35084+, A? record for yummyrecipesforme.com). Instead of a normal DNS reply the server responded over ICMP with udp port 53 unreachable.

What that means: port 53 is the well-known port for DNS. An ICMP “port 53 unreachable” reply strongly suggests the DNS server is not answering — either the service is down, or a firewall is dropping traffic destined for port 53.

Likely root causes if the server is actually down: a successful DoS attack against the DNS service, or a configuration error on the server itself.

Next steps I recommended: confirm whether the DNS service process is running, check the firewall for a rule blocking port 53, and check for a traffic spike / abnormal ICMP volume that would indicate an active attack.

Incident report analysis — DoS via ICMP flood, framed against NIST CSF

Scenario: a multimedia company (web design / graphic design / social media) suffered a two-hour DoS. Attackers sent an ICMP-flood through an unconfigured firewall. Response team blocked ICMP, took non-critical services offline, and restored critical services. I mapped the whole event to the NIST CSF:

NIST CSF functionWhat I documented
IdentifyReviewed affected systems, network devices, firewall settings. Root cause: an unconfigured firewall let excessive ICMP through, enabling an ICMP-flood DoS that took the internal network down and left users unable to reach network resources for about two hours.
ProtectFirewall rule to rate-limit incoming ICMP; IDS/IPS that screens ICMP for suspicious characteristics; a regular cadence for reviewing firewall configuration; routine security audits.
DetectNetwork monitoring software + firewall logs + IDS to watch incoming ICMP, flag abnormal traffic patterns, spot spoofed source addresses, and raise an alert when something looks off.
RespondIsolate affected systems so the disruption cannot spread; bring critical services back online; comb network logs for suspicious activity; escalate to upper management and legal / regulators when required.
RecoverRecover systems hit by the ICMP flood (internal network services + firewall configuration). Verify each service against network backups, system logs and monitoring data. Restore firewall settings to a secure baseline. Re-enable monitoring + IDS/IPS to confirm no residual malicious traffic.

My takeaway: properly configured firewall rules and ongoing network monitoring are the difference between an ICMP flood being an inconvenience and a two-hour outage. IDS/IPS and traffic rate-limiting are essential preventive controls.

Security risk assessment report — three hardening measures I prioritised

  1. Multi-factor authentication (MFA) — require more than one independent factor (biometric, physical ID card, PIN, password) before an app grants access. Even if a password is brute-forced or shared, the second factor stops the attacker; because a borrowed password is much less useful, sharing is discouraged in the first place.
  2. Company-wide password policy — minimum length, permitted character set, no credential sharing, and account lockout after N (e.g. five) consecutive failed logins. Complexity + rotation + no-reuse rules add friction that slows a brute-force attacker.
  3. Regular firewall maintenance — keep the allow / deny ruleset aligned with current standards; move suspicious sources onto the deny list; revisit the ruleset after every security event where unwanted traffic got through. Kept current, this control defends against a range of DoS / DDoS attacks.

Analyse network attacks — SYN flood diagnosis

Scenario: users reported connection-timeout errors on a website. Working through the packet logs, I saw the web server stop answering right after a heavy burst of SYN packets. Classic SYN flood, a variant of DoS.

How the attack breaks the site:

  1. The TCP three-way handshake normally runs: client SYN → server SYN-ACK → client ACK.
  2. On the SYN-ACK the server reserves memory and a connection-table slot for that session.
  3. In a SYN flood, the attacker fires many SYNs and never completes the handshake. The server’s connection table fills with half-open sessions; nothing is left for legitimate requests.
  4. The server can’t open new connections, so real users see connection-timeout messages.

Countermeasures I’d apply: SYN cookies at the server, rate-limiting at the firewall, IDS/IPS signatures for flood behaviour, and upstream DDoS-protection service for large-scale attacks.

Apply OS hardening techniques — HTTP-based compromise + brute-force response

Protocol involved: HTTP (application-layer). Confirmed by tcpdump capture while loading yummyrecipesforme.com; the malicious download was also delivered over HTTP.

How the incident unfolded:

  1. Customers reported the site was prompting them to download and run a file advertised as new recipe content; their PCs then ran slowly.
  2. The site owner was locked out of the admin account.
  3. I opened the site in a sandbox to keep production safe, started tcpdump, and reproduced the prompt.
  4. Accepting the download redirected the browser to a spoofed site: greatrecipesforme.com.
  5. tcpdump showed the browser first resolved yummyrecipesforme.com and established the HTTP connection, then abruptly resolved a new IP for greatrecipesforme.com and rerouted traffic there.

Working theory: attacker brute-forced the admin account, changed the password, and injected malicious code into the legitimate site to push a file disguised as a browser update. End-user compromise happened once that file was executed.

Remediations for brute-force I recommended:

  • Block password reuse — the original foothold used a default password; policy must prevent any prior or default password being reused on reset.
  • Shorten password-rotation interval — if a credential ever leaks, tighter rotation limits how long the stale password is useful.
  • Two-factor authentication (2FA) — pair the password with a one-time passcode (OTP) sent to email or phone. Even a successful brute-force of the password by itself is no longer enough.

Pitfalls I stay aware of

  • Confusing DoS with DDoS — DoS is one source; DDoS is many (a botnet). Countermeasures differ: rate limiting handles small DoS; DDoS usually needs an upstream provider.
  • Assuming ICMP is safe to leave wide-open — ICMP is useful diagnostically, but an unconfigured firewall + ICMP = easy DoS.
  • Confusing MAC with IP address — MAC is L2 hardware identity, IP is L3 routable identity. A router changes the source/destination MAC hop-by-hop, but not the IP.
  • Trusting a firewall as if it were the whole answer — it’s one layer; defence in depth requires OS hardening, MFA, EDR, monitoring and least privilege too.
  • Reading tcpdump without checking direction — forgetting who’s the source and who’s the destination flips the whole story of the trace.
  • Missing the L4 vs L7 distinction — a SYN flood is L4 (TCP handshake exhaustion); a Slowloris or HTTP flood is L7 (application). They need different mitigations.

Additional network-security concepts I know

  • On-path attack (MITM) — attacker positions between two endpoints, intercepts and can modify traffic.
  • Passive packet sniffing — attacker observes traffic silently, doesn’t alter it. Active packet sniffing — attacker manipulates traffic (injects, alters, redirects).
  • IP spoofing — forge source IP to bypass IP-based filters or hide origin.
  • Smurf attack — DDoS combining IP spoofing + broadcast ICMP amplification.
  • Ping of death — malformed / oversized ICMP packet designed to crash the target’s IP stack.
  • Replay attack — capture then re-transmit valid traffic to gain unauthorised access.
  • ICMP flood — overwhelm the target with ping requests.
  • Controlled zone — part of the network segmented from unauthorised access (behind firewall + IAM). Uncontrolled zone — the untrusted network outside those controls (the internet).
  • DMZ (Demilitarised Zone) — a controlled subnet that hosts internet-facing services (web, mail, DNS) so they never sit on the fully-internal network.
  • Forward proxy server — sits between users and the internet; represents users to external services (used for policy enforcement, caching). Reverse proxy server — sits between external users and internal services; represents the service (used for load balancing, TLS termination, WAF).
  • Cloud-based firewalls — firewall functionality delivered as a cloud service (FWaaS). Elastic, centrally managed; ideal for multi-cloud / hybrid environments.
  • Port filtering — explicitly allow only the ports the org uses, block everything else at the firewall.
  • IEEE 802.11 (Wi-Fi) — the wireless-LAN standard family. Security evolves through WPA → WPA2 → WPA3 (WPA3 adds forward secrecy and a stronger handshake).
  • Bandwidth — the maximum data-transfer capacity of a network link (Mbps / Gbps). Attacks like DDoS aim to consume it.

Broader concepts I’m fluent in that expand on the above

  • Zero trust architecture — identity- and context-based access with continuous verification, replacing the “castle and moat” perimeter model.
  • Network segmentation and micro-segmentation — separate high-value assets from user segments; contain blast radius when one segment is compromised.
  • TLS handshake at high level — client hello → server hello + cert → verify cert chain → key exchange → encrypted channel. Understanding this makes it easier to interpret HTTPS captures.
  • My RAN side of this stack — IPsec/IKEv2 at the security gateway, PKI + certificate enrollment on the femto, SUPI/SUCI concealment and the 5G AKA key hierarchy (K → K_AUSF → K_SEAF → K_AMF → K_gNB). I already work at the seam where network security meets telecom.
