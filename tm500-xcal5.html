TM500 & XCAL5 — Lab Tools User Guide

TM500 and XCAL5 are the two RAN-lab tools I drive most. TM500 is a hardware UE network tester — it simulates many UEs at once to load and stress-test the gNB / eNB. XCAL5 is a software signalling analyzer — it captures L1/L2/L3 messages from a real UE so I can decode RRC, NAS, MAC/PHY and SIP behaviour in detail. This page is a short user guide on what each tool is, how I set it up, and how I use them together in a typical 5G SA validation session.

What each tool is — in one line

ToolWhat it isWhat I use it for
TM500A hardware UE / mobile-network tester that emulates many UEs at once against a real gNB / eNB. Sits in a rack, has RF ports, and is driven from a Windows-based GUI / test environment on a control PC.Multi-UE attach / registration capacity, PDU-session throughput, mobility (handover) stress, RRC / PRB / CPU KPI generation, soak runs.
XCAL5A Windows-based UE-side signalling analyzer. Connects to a real UE over USB (chipset diag mode) and decodes L1/L2/L3 in real time — RRC, NAS, MAC, PHY, SIP, IMS — with a built-in log player and call-flow view.Decoding the air-interface and IMS / SIP, root-causing a single UE’s attach / call / data behaviour, walking SIB content, checking RRC events, capturing VoNR / RTT call flow.

TM500 — basic workflow

  1. Plan the test. Decide how many UEs, which services (attach only, attach + PDU session, attach + VoNR + data, mobility), the band / carrier under test, and how long the run is.
  2. Configure the network parameters on TM500: PLMN, tracking-area code, NR band / ARFCN / bandwidth, SSB config and SCS. These have to match the gNB’s broadcast or no UE will attach.
  3. Configure the UE profile: IMSI / SUPI range so the AMF / UDM recognises them, UE category / capability, and how many simulated UEs to bring up. Match the SIM provisioning at the core.
  4. Build the test script — the ordered sequence each simulated UE will run: power-on → attach / 5G NAS Registration → PDU Session Establishment → offered traffic profile (DL/UL TCP/UDP, configurable bitrate) → optional handover → deregister. TM500 has GUI building blocks for each step; complex scripts are saved and reused per campaign.
  5. Connect RF from the TM500 RF ports through an attenuator network to the gNB’s RF chain. The attenuator lets me simulate cell-centre / mid / edge without moving anything physically — just sweep the attenuation.
  6. Run & monitor. Start the test and watch the live counters: UE-attached count, RRC success ratio, PDU-session success ratio, throughput per UE, BLER, MCS, CQI, and the gNB-side KPIs from the OAM (PRB, CPU, scheduler fairness).
  7. Export the run report — CSV / Excel of all KPIs over time, plus the captured logs — for the regression record.
💡Typical campaigns I run on TM500: RRC / context / QoS-flow success ratios at scale, PRB / CPU utilization under offered load, throughput fairness across N UEs, mobility stress (handover success ratio at N HO/s), and soak runs (8-hour VoNR, 24-hour data).

XCAL5 — basic workflow

  1. Connect the UE to the PC over USB. The UE has to be in diag mode (Qualcomm / Samsung chipsets, depending on the model) so XCAL5 can pull layer-by-layer logs from it.
  2. Open XCAL5 and select the UE. XCAL5 auto-detects the chipset and shows the connected device in its UE list. If multiple UEs are connected, each gets its own pane.
  3. Pick which layers to log. A typical 5G validation run captures RRC, NAS-5GS, MAC, PHY, IP, SIP / IMS. For VoNR I always include SIP.
  4. Start logging. XCAL5 begins writing the capture file — both the raw chipset log and the decoded messages stream in live.
  5. Run the scenario. On the UE: power-on / attach, make a VoNR call, push data, trigger a handover — whatever the test case is. XCAL5 records everything timestamped to the test session.
  6. Analyze. Stop the capture and walk through the call flow:
    • RRC Setup → NAS Registration Request → Authentication → Security Mode → Registration Accept → PDU Session Establishment.
    • Use the filter bar to isolate one message type (e.g. only RRCReconfiguration or only SIP).
    • For VoNR, jump into the SIP call-flow view: INVITE → 100 Trying → 183 Session Progress → 180 Ringing → 200 OK → ACK.
    • Export filtered events to CSV / TXT for the report and attach the raw XCAL5 capture to the test case.
🔎What I look at first when an attach fails on XCAL5: SIB1 read (cell access / barred?), then RRC Setup Request cause, then NAS Registration Request → Reject (and the 5GMM cause), and finally the Security Mode Command/Complete exchange. Most "won’t attach" cases are clear within the first few messages once the log is in front of you.

How I use them together in a single test session

For a real 5G SA Femto validation campaign the three tools work in parallel:

ToolRole in the session
TM500Generates the offered load — many simulated UEs attaching, holding PDU sessions, sending data, handing over — so the gNB and core are exercised at scale. Runs the campaign script and produces the KPI report.
XCAL5Captures the detailed UE-side signalling on a "golden" real UE (a known device on the same cell). When TM500 surfaces a counter regression, XCAL5 tells me what the UE actually saw on the air interface.
Wireshark / tsharkCaptures the core-facing signalling at the AMF / UPF / SeGW — NGAP / NAS / SCTP / IPsec — via my Python+tshark validators. Closes the loop: UE side from XCAL5, core side from Wireshark, system-level KPIs from TM500.

If TM500 reports an RRC-setup-failure spike, I pull XCAL5 logs from the golden UE for the same window and the tshark capture from the AMF. Between the three I can pin the failure to a layer (radio, RRC, NAS, NGAP, IPsec) and a node (UE, gNB, AMF, SeGW) very quickly.

Practical setup checklist

  • SIM / SUPI alignment: the UE’s SUPI must match what the AMF / UDM has provisioned — for TM500 simulated UEs and for the real UE driven by XCAL5.
  • Attenuator network: a controlled attenuator between TM500 / UE RF and the gNB lets me sweep cell-centre → cell-edge without moving anything. Plan the path loss range up front.
  • Band-lock the UE on the band under test, so the UE doesn’t silently camp on LTE while I’m trying to test NR.
  • Log everything during the run. Re-decoding a saved log is much faster than re-running a multi-hour soak.
  • Naming convention for captures: <testcase>_<date>_<UE-ID>_<run>.<ext>. Without it the regression archive is unsearchable in a week.

Field notes

  • TM500 is a system test, not a UE test. It tells me whether the gNB handles the load and signalling at scale — not whether one specific handset model works (that’s XCAL5 territory).
  • XCAL5 is only as good as the UE diag access. If the device-mode (diag port) isn’t open, no logs.
  • The two tools are complementary, not interchangeable. Use TM500 for KPI and capacity; use XCAL5 for "what did the UE actually see" on a single device.
  • For VoNR-specific work: XCAL5 SIP + RTP stats catch garbled-audio / jitter / setup-time issues that TM500 alone can’t see (see VoNR page).
