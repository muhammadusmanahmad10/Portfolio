Tools of the Trade: Linux and SQL

The two everyday tools of a security analyst. Linux is where investigations happen — the shell, the filesystem, users and permissions. SQL is how I ask questions of security-log tables (login attempts, employee records, machine inventory). This page is how I think about both, plus the labs I completed to prove it.

Operating-system fundamentals

An operating system mediates between hardware and applications — kernel, device drivers, processes, memory, file system, user accounts, network stack. Every action on a machine passes through the OS boundary of authentication → authorisation → audit.

Common OS families I know: Linux (Kali, Parrot, Ubuntu, Debian, RHEL, CentOS), Windows, macOS, ChromeOS. GUI vs CLI — CLI is preferred in security work for scripting, automation and forensic reproducibility.

Linux — the SOC everyday workspace

Anatomy of Linux

  • Open-source, Unix-like OS built around a kernel, a shell (default = Bash) and userland utilities.
  • Distributions used in security work: Kali Linux (pen-test), Parrot, Ubuntu, Debian, Red Hat Enterprise Linux (RHEL), CentOS.

Filesystem hierarchy

  • / — root of the filesystem
  • /root — root user’s home
  • /home — regular users’ homes
  • /etc — system configuration files
  • /var — variable data (logs, spool); /var/log for system + application logs
  • /tmp — temporary files
  • /bin, /sbin, /usr/bin — executable binaries

Commands

  • Navigation / inspection: pwd, ls (-l, -a, -la), cd, cat, head, tail (-f for live logs), less, wc.
  • Files & directories: touch, mkdir, rm (-rf), rmdir, mv, cp.
  • Search & filter: grep (-i, -r, -v, -c), find, pipes |, redirection > / >>, tee.
  • User & group management: whoami, sudo, useradd, userdel, usermod, groupadd, passwd.
  • Permissions: chmod (numeric 755 or symbolic u+x), chown, chgrp.
  • Help: man <cmd>, <cmd> --help.

The permission model I can read

Every Linux file has three permission triplets — user (owner) / group / other — and each triplet has read (r), write (w), execute (x).

Example: -rwxr-x--- means the leading - is a regular file (a d would be a directory); owner has r+w+x; group has r+x; other has nothing.

How the 10 characters break down:

  • Position 1: file type — d = directory, - = regular file.
  • Positions 2–4: rwx for the owner (user).
  • Positions 5–7: rwx for the group.
  • Positions 8–10: rwx for other.

Principle of least privilege at the OS level: give every account only the access it strictly needs. Use sudo instead of logging in as root.

SQL — how I query security data

Core concepts

  • Relational database — data organised into tables of rows and columns, related by keys.
  • Primary key uniquely identifies each row; foreign key references another table’s primary key to enforce a relationship.
  • Why analysts query — investigating login attempts, employee records, machine inventory, alerts.

Query pattern I use

  • Basic query: SELECT col1, col2 FROM table WHERE cond ORDER BY col;
  • Filtering: =, <, >, BETWEEN…AND, LIKE '%text%', IN (…), IS NULL.
  • Combining conditions: AND, OR, NOT.
  • Aggregates: COUNT(), SUM(), AVG(), MIN(), MAX(), GROUP BY, HAVING.
  • Wildcards with LIKE: % matches any sequence of characters (e.g. 'MEX%' matches both MEX and MEXICO).

Joins — when the answer lives in more than one table

  • INNER JOIN — only rows that match in both tables.
  • LEFT JOIN — all rows from the left table; matches from the right where they exist.
  • RIGHT JOIN — mirror of LEFT JOIN.
  • FULL OUTER JOIN — all rows from both sides.

Deliverables I produced

Applied SQL filters to real security-log investigations

My organisation was hardening its systems. My role was to keep the systems safe, investigate anything suspicious, and identify machines that needed patching. I used SQL against two tables — log_in_attempts and employees — to isolate exactly what each task needed. Six real query patterns I wrote:

  1. After-hours failed logins — every failed sign-in after 18:00 needed a closer look. 
    -- Failed logins after business hours
SELECT * FROM log_in_attempts
WHERE  login_time > '18:00' AND success = FALSE;
    Why: a possible security incident happened outside business hours — combine two conditions with AND so both must hold.
  2. Login attempts on specific dates — suspicious activity flagged on 2022-05-09, so any logins from that day or the day before are of interest. 
    -- Logins on 2022-05-08 OR 2022-05-09
SELECT * FROM log_in_attempts
WHERE  login_date = '2022-05-09' OR login_date = '2022-05-08';
    Why OR: a row matching either date should return.
  3. Login attempts outside Mexico — foreign logins stand out as likely problems. 
    -- Everything except Mexico (stored as MEX or MEXICO)
SELECT * FROM log_in_attempts
WHERE  NOT country LIKE 'MEX%';
    Why LIKE + %: country field stores both MEX and MEXICO; the percent-sign wildcard matches either.
  4. Machines belonging to Marketing employees in the East building — needed to push an update. 
    -- Marketing staff in the East building
SELECT * FROM employees
WHERE  department = 'Marketing' AND office LIKE 'East%';
    Why both conditions: AND requires both to hold; East% matches any office number in the East building.
  5. Machines belonging to Finance OR Sales employees — a different update for those two departments. 
    -- Finance or Sales
SELECT * FROM employees
WHERE  department = 'Finance' OR department = 'Sales';
    Why OR: anyone in either department qualifies.
  6. Everyone outside IT — final update needed to reach non-IT staff. 
    -- Everyone not in IT
SELECT * FROM employees
WHERE  NOT department = 'Information Technology';
    Why NOT: exclude a single department from the result set.

Summary: across all six tasks I used AND, OR, NOT, and LIKE with % wildcards against two tables to isolate exactly what each investigation needed — the same pattern I’d apply to any SIEM-adjacent log table.

Corrected Linux file permissions on a research team’s project directory

Scenario: the research team’s projects directory had permissions that didn’t match the authorisation each item should carry. My job was to review and correct them so the team’s system stayed secure.

Step 1 — check current file and directory details:

# long-format listing including hidden files
ls -la

The output showed one directory (drafts), one hidden file (.project_x.txt, hidden because the name starts with .), and five project files. The 10-character permission string in the first column encoded who could do what.

Worked example — project_t.txt had string -rw-rw-r--. Leading - means regular file. Owner and group have read + write. Other has read only. Nobody has execute.

Step 2 — remove write access from other on project_k.txt:

# strip write from "other" on project_k.txt
chmod o-w project_k.txt
ls -la

Step 3 — archived hidden file needed read-only for user + group, nothing for other:

# overwrite permissions on the hidden archived file
chmod u=r,g=r .project_x.txt
ls -la

Overwrote existing permissions in one shot: u=r = user read-only, g=r = group read-only, everything else cleared.

Step 4 — only user researcher2 should be able to enter the drafts directory:

# take execute permission away from group on the drafts directory
chmod g-x drafts
ls -la

The user researcher2 already had execute permission, so no addition was needed. Removing the group’s execute means only researcher2 can descend into drafts.

Summary: workflow is always ls -la → interpret the 10-character string → chmod → ls -la again to confirm. Symbolic (u+x, o-w, u=r,g=r) is fine for one-off changes.

Pitfalls I stay aware of

  • Confusing AND vs OR — a wrong operator changes an investigation completely (“Marketing AND East building” is a very different result from “Marketing OR East building”).
  • Forgetting to quote strings — WHERE country = MEX fails; must be = 'MEX'.
  • Missing wildcard cases — if the data has both MEX and MEXICO, an = match misses half; use LIKE 'MEX%'.
  • Running rm -rf as root without checking the path — classic irrecoverable mistake; there is no undo in Linux.
  • Editing permissions on the wrong file / user account — always ls -la immediately before and after the change.
  • Forgetting to use sudo for admin tasks — leads to noisy “permission denied” errors and time wasted.

Additional OS & database concepts I know

  • Bootloader — the program that loads the OS kernel into memory during boot.
  • Kernel — the OS core that mediates between hardware and user-space processes; manages memory, CPU scheduling, drivers, syscalls.
  • CPU (Central Processing Unit) — the chip that executes instructions.
  • Peripheral devices — keyboards, mice, printers, external drives, headsets. Some (USB drives) are attack surfaces in themselves.
  • Legacy operating system — an old / end-of-life OS still in production. Often unpatched and disproportionately risky — should be inventoried, isolated and monitored.
  • Filesystem Hierarchy Standard (FHS) — the standard that defines the Linux directory layout (/etc, /var, /usr, etc.). Why it matters: it lets analysts know exactly where to look on any Linux system.
  • Root directory — the top of the filesystem, written as / on Linux. Not to be confused with the root user’s home (/root).
  • Absolute path — a full path starting from / (e.g. /var/log/syslog). Relative path — a path from the current working directory (e.g. logs/syslog).
  • Wildcard — a symbol standing in for other characters. On the shell: * (any characters), ? (single character). In SQL LIKE: % (any sequence) and _ (single char).
  • Standard input / output / error — the three default streams a process reads / writes: stdin, stdout, stderr. Redirected with <, >, 2>.
  • World-writable file — a file whose permission triplet gives “other” write access. Almost always a mistake — anyone on the system can modify it.
  • User interface (UI) — GUI vs CLI; SOC work leans CLI for scripting and reproducibility.

Broader concepts I’m fluent in that expand on the above

  • Regex with grep — pattern matching on logs (e.g. grep -E "^ERROR|FATAL" /var/log/syslog).
  • Piping SQL with Linux tools — export a query result to CSV, then grep, sort, uniq -c, awk for quick pivots.
  • Bash scripting for automation — wrap a repeated investigation into a script; the same discipline I apply to my Python + tshark validators.
  • Sudoers file discipline — grant specific commands rather than blanket root access.
