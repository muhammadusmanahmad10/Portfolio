The eight security domains — in depth

The CISSP-defined categorisation use to organise security work and spot coverage gaps:

  1. Security & Risk Management — defining security goals, risk mitigation, compliance, business continuity, legal regulations, professional ethics. Also covers InfoSec disciplines: incident response, vulnerability management, application security, cloud security, infrastructure security. Example: adjusting how PII is treated to meet GDPR.
  2. Asset Security — managing storage, maintenance, retention and destruction of physical and virtual data. Includes security-impact analysis, recovery plans, data-exposure management. Example: overseeing hard-drive destruction so private data can’t be recovered.
  3. Security Architecture & Engineering — effective tools, systems and processes to protect assets and data. Core concept: shared responsibility. Design principles that live here: threat modelling, least privilege, defence in depth, fail securely, separation of duties, keep it simple, zero trust, trust but verify. Example: using a SIEM to spot unusual logins that hint at a threat actor.
  4. Communication & Network Security — securing physical networks and wireless comms across on-site, remote and cloud. Handles Bluetooth / public Wi-Fi risks. Example: restricting network access so remote workers reach the org securely.
  5. Identity & Access Management (IAM) — four components:
    • Identification — user claims identity (username, access card, biometric).
    • Authentication — verify identity (password, PIN, MFA).
    • Authorisation — what the identity can do once verified (least privilege by role).
    • Accountability — monitor + record user actions (login attempts, actions taken) for audit.
    Example: give a customer-service rep read-only access to a customer’s phone number only while resolving the ticket, then revoke.
  6. Security Assessment & Testing — control testing, data analysis, security audits, penetration testing. Example: audit user permissions regularly so nobody accumulates unnecessary access.
  7. Security Operations — investigations + preventative measures. Uses training / awareness, reporting, IDS/IPS, SIEM, log management, incident management, playbooks, post-breach forensics, lessons learned. Example: respond to an unknown device appearing on the internal network.
  8. Software Development Security — secure coding baked into every SDLC phase (design review during design; secure code review during development / testing; pen testing during deployment). Example: pharma company’s new medical device must have encryption configured before shipping.

Threats, risks, vulnerabilities

  • Threat — any circumstance or event that can negatively impact assets (social engineering, malware).
  • Risk — anything that can impact confidentiality, integrity or availability of an asset. The likelihood of a threat occurring. Analogy: risk is being late to work; threats are traffic, an accident, a flat tire.
  • Vulnerability — a weakness that a threat can exploit. Both a vulnerability AND a threat must be present for a risk to exist.

Risk levels:

  • Low — info whose loss would not harm reputation, operations or finances (e.g. published research, website content).
  • Medium — not public; could cause some damage (e.g. early leak of quarterly earnings).
  • High — info protected by law / regulation; severe damage if compromised (SPII, PII, IP).

Common vulnerabilities: outdated firewall / software / applications, weak passwords, unprotected confidential data, un-trained people (the human vulnerability).

Named threats, risks and vulnerabilities I’m aware of

Threats: insider threats, advanced persistent threats (APTs).

Risk-affecting factors:

  • External risk — anything outside the org (threat actor attempting private-info access).
  • Internal risk — current / former employee, vendor or trusted partner.
  • Legacy systems — old workstations / mainframes not tracked or updated; a vending machine that still takes credit cards; a workstation still connected to a legacy accounting system.
  • Multiparty risk — outsourcing to third parties that gain access to trade secrets / software designs.
  • Software compliance / licensing — software not updated / non-compliant; unpatched vulnerabilities.

Specific vulnerabilities:

  • ProxyLogon — pre-authenticated vulnerability affecting Microsoft Exchange; attacker deploys code remotely.
  • ZeroLogon — vulnerability in Microsoft Netlogon authentication protocol.
  • Log4Shell — lets attackers run Java code on someone else’s computer or leak sensitive info; remote takeover of internet-connected devices.
  • PetitPotam — affects Windows NTLM; LAN-based attacker forces an authentication request.
  • Security logging & monitoring failures — insufficient logging so attackers exploit vulns undetected.
  • Server-side request forgery (SSRF) — attacker manipulates a server-side app to access / update backend resources or steal data.

Where I look them up in real work: NIST National Vulnerability Database (NVD), CISA Known Exploited Vulnerabilities Catalog, OWASP Top 10.

Ransomware and the three layers of the web

Ransomware encrypts an organisation’s data and demands payment for a decryption key. Can freeze systems, leave devices unusable, and lock confidential data. Negotiations and leaked data usually surface on the dark web.

The three layers of the web:

  • Surface web — content accessed via a normal browser (public sites).
  • Deep web — requires authorisation (e.g. an org’s intranet).
  • Dark web — only accessible via special software; where stolen PII is sold and ransom negotiations happen.

The three key impacts of threats / risks / vulnerabilities:

  1. Financial — interrupted production, cost to fix, fines from non-compliance.
  2. Identity theft — PII/SPII sold or leaked on the dark web.
  3. Reputation damage — customers leave, bad press, legal penalties, permanent brand damage.

Risk-management strategies

  • Acceptance — accept a risk to avoid disrupting business continuity.
  • Avoidance — create a plan to avoid the risk entirely.
  • Transference — transfer the risk to a third party (e.g. cyber-insurance).
  • Mitigation — lessen the impact of a known risk (patch, add MFA, add a control).

NIST Risk Management Framework (RMF) — the seven steps

  1. Prepare — activities needed to manage security and privacy risks before a breach. Monitor for risks, identify controls that reduce them.
  2. Categorize — develop risk-management processes and tasks by thinking about how CIA of systems and information can be impacted. Follow the org’s processes to reduce risk to critical assets like customer info.
  3. Select — choose, customise and document the controls that protect the org. Keep playbooks up to date; help manage documentation.
  4. Implement — implement security and privacy plans. Example: if employees keep needing password resets, change the password requirements.
  5. Assess — determine if established controls are implemented correctly. Identify weaknesses and decide whether tools / procedures need to change.
  6. Authorize — own the security and privacy risks that may exist. Generate reports, develop plans of action, establish project milestones aligned to security goals.
  7. Monitor — be aware of how systems are operating; daily assessment and maintenance of technical operations.

Other frameworks in this space: HITRUST (Health Information Trust Alliance).

Frameworks vs controls

Security frameworks — guidelines used for building plans to mitigate risks and threats to data and privacy. Four core components of a framework:

  1. Identify and document security goals.
  2. Set guidelines to achieve those goals.
  3. Implement strong security processes.
  4. Monitor and communicate results.

Security controls — safeguards designed to reduce specific risks. Used with frameworks to build strong security posture.

CIA triad

  • Confidentiality — only authorised users can access assets or data. Enforced by encryption, access control, MFA, least privilege.
  • Integrity — data is correct, authentic and reliable; not tampered with. Enforced by hashing, digital signatures, checksums, HMAC.
  • Availability — data is accessible to those authorised. Enforced by backups, redundancy, DDoS protection.

Frameworks I know by name

  • NIST CSF (Cybersecurity Framework) — five functions: Identify · Protect · Detect · Respond · Recover.
  • NIST RMF (Risk Management Framework) — seven steps (see above).
  • Federal Energy Regulatory Commission — NERC (FERC-NERC) — applies to organisations working with the North American power grid.
  • Federal Risk and Authorization Management Program (FedRAMP) — US federal cloud security framework.
  • Center for Internet Security (CIS) Controls — prioritised safeguards for the most common attacks.
  • GDPR (General Data Protection Regulation) — EU data-privacy law; 72-hour breach-notification rule.
  • PCI DSS (Payment Card Industry Data Security Standard) — controls for organisations that handle cardholder data.
  • HIPAA — US health-data regulation.
  • ISO / IEC 27001 — international information-security management standard.
  • SOC 1 and SOC 2 — audit reports covering financial (SOC 1) and trust-service criteria (SOC 2: security, availability, processing integrity, confidentiality, privacy).

Security controls — categories and types

Three categories (family of the control):

  • Administrative / managerial — policies and procedures that address the human side (acceptable-use policy, on-boarding / off-boarding, training).
  • Technical — firewalls, IDS/IPS, antivirus / EDR, encryption, MFA, IAM.
  • Physical — door locks, cabinet locks, CCTV surveillance, badge readers.

Four types (the effect the control has — and a single control can span types):

  • Preventative — stops a threat before it happens (firewall rule blocking a port).
  • Detective — identifies a threat as it happens (SIEM alert on failed logins).
  • Corrective — fixes / recovers after an incident (restore from backup, apply a patch).
  • Deterrent — discourages would-be attackers (visible CCTV, warning banners).

Security ethics

  • Confidentiality — do not share confidential info without a business reason.
  • Privacy protections — safeguard PII / SPII; only collect and retain what’s needed.
  • Laws — comply with GDPR, HIPAA, PCI DSS, CCPA and local regulations.

SIEM tools and dashboards

Logs — the raw material

  • Firewall logs — attempted / established inbound and outbound traffic.
  • Network logs — devices entering / leaving the network and connections between them.
  • Server logs — events on services: websites, email, file shares. Includes login, password, username requests.

SIEM — what, why, how

What: Security Information and Event Management — application that collects and analyses log data to monitor critical activities. Provides real-time visibility, automated alerts, centralised storage.

Why: without SIEM you drown in raw logs. It indexes and reduces what an analyst reviews manually and correlates events across sources you couldn’t otherwise link.

How: collect → normalise → correlate against rules → alert → surface on dashboards.

Deployment models: self-hosted (best when data must stay on-prem), cloud-hosted (vendor manages infra), cloud-native (designed for cloud, scalable / flexible / highly available), hybrid.

SOAR (Security Orchestration, Automation and Response) — a collection of apps, tools and workflows that use automation to respond to security events. Handles common events without waiting for a human, freeing analysts for complex incidents.

Tools and dashboards

Splunk Enterprise (self-hosted), Splunk Cloud (cloud-hosted), Google Chronicle (cloud-native).

Splunk dashboards:

  • Security posture — last 24 h of notable events; SOC real-time monitoring.
  • Executive summary — high-level view for stakeholders.
  • Incident review — visual timeline of events leading up to an incident.
  • Risk analysis — risk per object (user, machine, IP); helps prioritise mitigation.

Chronicle dashboards:

  • Enterprise insights — recent alerts; suspicious domain IOCs with confidence + severity.
  • Data ingestion & health — event-log volume, log sources, ingestion success rate.
  • IOC matches — top threats over time by domain, IP, device IOC.
  • Main dashboard — timeline of security events (e.g. failed-login spike).
  • Rule detections — incidents by severity and occurrence; per-rule alert lists.
  • User sign-in overview — access behaviour; catches users signing in from multiple locations at once.

Metrics from a dashboard: response time, availability, failure rate.

Practical exercise I completed — SIEM tabletop for an e-commerce outage

Walked through this scenario with an AI-guided coach: a company’s main e-commerce website went offline; customers couldn’t access it.

  • Server logs — when did the site go down, what caused the crash, what errors, what resources.
  • Firewall logs — external or internal attack? Who tried and when? What was blocked / allowed?
  • Network-device logs — source IPs of the suspicious traffic; unusual patterns.
  • Application logs — user interactions, transactions, internal errors, location of activity.

How SIEM helped: centralised log management (one place, one search), automated alerting (rule fires on failed-login spike from a suspicious IP), event correlation (link a blocked firewall attempt to an app error at the same moment), dashboards with severity to prioritise. Proactive value: continuous monitoring + rule tuning + severity prioritisation + alert correlation lets me catch incidents before they escalate.

Playbooks and incident response

What a playbook is

A playbook is a manual containing the operational steps for a specific event type. In security it’s a documented set of manual + automated actions that make response consistent, faster and auditable. Common types: incident-response playbooks, vulnerability-management playbooks, product-specific runbooks.

The six phases of an incident-response playbook

  1. Preparation — policies, playbooks, tooling, training, contact lists.
  2. Detection & analysis — recognise events, triage, verify, classify severity, scope the incident.
  3. Containment — stop the bleeding: isolate hosts, block IPs, disable accounts.
  4. Eradication & recovery — remove the attacker’s foothold, patch, restore from clean backup, harden.
  5. Post-incident activity — lessons learned, playbook update, evidence retention, root-cause analysis.
  6. Coordination — who to notify (SOC lead, legal, comms, execs, customers, regulators) and when.

Escalation criteria the playbook drives: severity, scope, sensitivity, regulatory impact.

Documentation discipline: incident handler’s journal (timestamped notes), chain of custody for evidence, one ticket per incident.

How SIEM + playbook + analyst work together

  1. SIEM detects an alert (e.g. large data volume moved outside working hours).
  2. Analyst opens the playbook for that alert type.
  3. Follow triage steps → verify vs false-positive.
  4. If real, follow containment → eradication → recovery steps.
  5. After the incident, do a post-mortem and update the playbook so the next analyst is faster.

How to run a security audit

A security audit is a review of an organisation’s security records, activities and related documents to identify areas of improvement and confirm controls are working. Audits are internal (SOC / IT) or external (regulators / third parties).

Internal-audit workflow (applied on Botium Toys):

  1. Establish scope and goals.
  2. Conduct a risk assessment of assets, threats, risks and vulnerabilities.
  3. Complete a controls assessment — document controls in place vs missing.
  4. Assess compliance against the frameworks the org is subject to.
  5. Communicate results to stakeholders with prioritised recommendations.

Recommendations I delivered to the IT manager / stakeholders

  • Least privilege — employees only access data required for their role.
  • Separation of duties — split CEO’s day-to-day and payroll responsibilities.
  • Encryption — encrypt cardholder and customer data at rest, in transit, in use.
  • Password management system + stronger password policy.
  • Disaster-recovery plan + regular backups.
  • Intrusion detection system (IDS).
  • Ongoing legacy-system management on a defined schedule.
  • Formal asset classification and inventory so the right controls apply per class.

Pitfalls I stay aware of

  • Treating a framework as a checklist — NIST CSF / RMF are continuous processes, not one-off audits.
  • Confusing control category and control type — category is who / what the control works on (admin / technical / physical); type is the effect (preventive / detective / corrective / deterrent). A single control can span types.
  • Ignoring physical controls — locks, CCTV and badge readers are as much a part of the posture as firewalls and encryption.
  • Skipping the compliance layer — controls without a mapping to the frameworks the org is subject to (PCI DSS, GDPR, HIPAA, SOC 2) leave auditable gaps.
  • Missing the risk-vs-threat-vs-vulnerability distinction — you need a threat AND a vulnerability for a risk to exist; missing either half changes the response.
  • Not updating the playbook after an incident — the post-incident update is the difference between a SOC that gets better and one that keeps repeating the same investigation.
  • Following the SIEM dashboard blind — dashboards are visualisations; if the underlying log ingestion breaks, the dashboard lies.

Additional risk / continuity concepts I know

  • Business continuity plan (BCP) — the org-wide plan that keeps critical business functions running during and after a disruption. Focus: people, processes, customers.
  • Disaster recovery plan (DRP) — the IT-focused plan to restore infrastructure, systems and data after a disaster. Focus: technology, data, recovery time / point objectives (RTO / RPO).
  • Data owner — the senior business leader accountable for a data asset. Data custodian — the technical steward who implements the controls the owner defines.
  • Data controller — the entity determining the purpose / means of processing personal data (GDPR term). Data processor — the entity processing data on behalf of the controller.
  • Standards — formal, agreed rules an organisation adopts (ISO 27001, NIST, PCI DSS). Procedures — step-by-step instructions for how to carry a policy out. Policy sets direction; standards fix the rules; procedures walk the how.
  • Security governance — the leadership practices that support, define and direct security efforts across the org.
  • CVE Numbering Authority (CNA) — an organisation authorised to assign CVE IDs to newly discovered vulnerabilities.

Broader concepts I’m fluent in that expand on the above

  • Threat modelling methods — STRIDE (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege) and PASTA (Process for Attack Simulation and Threat Analysis). Both give a structured way to enumerate attacker paths through a design.
  • SIEM + SOAR + IoT + AI/ML trajectory — the SOC of the near future combines automated detection, automated response and analyst-in-the-loop for hard incidents.
