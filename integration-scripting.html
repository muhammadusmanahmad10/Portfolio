Multi-mode site architecture

Core configuration work — and what each actually means

OperationWhat it is & why it's done
SRAN conversionConsolidating separate single-RAT radios onto one multi-mode (Single RAN) platform so 2G/3G/4G/5G share baseband, transport and radios — cuts hardware, site visits and power.
BBU mergingCombining baseband units so multiple technologies/cells run from one BBU — frees slots and simplifies the site, but requires careful cell/clock/transport re-mapping in script.

Sector-carrier expansionAdding carriers/sectors for capacity — the script must extend cell, carrier, and resource mapping without disrupting live cells.
4T6S / Multi-RRUAdvanced radio topologies (4 transmit / 6 sector, multiple RRUs per cell) for coverage/capacity — sensitive to CPRI mapping and working-mode config.
MORAN / MOCNRAN sharing: MORAN = shared radio, separate carriers per operator; MOCN = shared carrier, multiple operators' core networks (multiple PLMNs broadcast).

Case study — one IPsec tunnel for two MMEs sharing a SeGW (ACL RULE + IPsec policy sequence)

Starting point
The baseline configuration built one IPsec tunnel per MME, even when the two MMEs sat behind the same Security Gateway (SeGW). The result was duplicate tunnels, duplicate ACL / IKEPEER / IPSECPOLICY objects, and extra control-plane load — with no real security or routing benefit because both MMEs were reachable through the same SeGW.
What I changed
Reworked the configuration so one ACL RULE could be bound to two IKEPEERs through the same Child SA. The ACLRULE destination IP / subnet was widened to cover the address ranges of both MMEs, and the IPSECPOLICY bound that single ACL rule to the shared SeGW peer — collapsing two tunnels into one.
The catch: IPsec policy sequence
Huawei IPSECPOLICY entries are matched in sequence (1, 2, 3, …) — the first matching rule wins. The widened “aggressive” ACL covers a broad subnet, so if it is placed early in the sequence it will also match traffic that should have used a more specific policy lower down the list — that traffic ends up sent through the wrong IKEPEER. Rule of thumb: aggressive / broad ACLs must sit at the bottom of the sequence; specific destinations go above them. Same principle as a router ACL — specific rules first, broad rules last.
The wildcard-vs-subnet-mask trap
The ACLRULE uses a wildcard mask on the destination, not a subnet mask — conceptually opposite to a subnet mask (bits that are wildcarded = 1, bits that must match = 0). For a subnet 10.0.0.0 / 255.0.0.0 (subnet-mask form), the equivalent ACL line is destination 10.0.0.0 with wildcard 0.255.255.255. If a subnet mask is mistakenly typed in the wildcard field (e.g. 255.0.0.0 instead of 0.255.255.255), the match window flips: it matches everything except the intended subnet, sending the wrong flows through the tunnel — effectively creating a routing loop / black-hole at the IPsec layer.
Concept & takeaway
For multiple peers sharing a SeGW, one tunnel + one ACL with the right wildcard + correct policy sequence is the cleaner design. Takeaway: the two things that bite you on Huawei IPsec are policy-match order (broad last, specific first) and the wildcard mask convention (inverse of a subnet mask). Both are silent failures — nothing alarms, traffic just goes the wrong way.

Case study — small-cell 3G cells not coming up because BASEBANDEQM couldn’t be bound from LMT

Symptom
During a small-cell integration the 3G (UMTS) cells would not come up. The cell objects existed and the rest of the site was healthy, but the cells sat in “not configured” / unavailable state.
Investigation
On the LMT (Local Maintenance Terminal) the configuration query that links the cell to its baseband equipment object showed no BASEBANDEQM binding for the affected cells, and the MML command needed to assign it wasn’t available in that session. This pointed to a limited MML package on the LMT — the package loaded onto the LMT didn’t expose the BASEBANDEQM-to-cell binding command for the small-cell board variant.
Fix
Brought the site under the central CME (Configuration Management Engine), where the full set of MOs / commands is available regardless of board variant. From the CME the cell’s BASEBANDEQM ID was assigned, the configuration was activated to the site, and the 3G cells came up on the next setup attempt.
Concept & takeaway
LMT and CME aren’t equivalent. LMT is the site-side maintenance tool and only exposes the MML commands present in the package it was loaded with — a slim package can hide objects/commands that the hardware actually supports. CME is the central, full-featured configuration tool. Takeaway: if a configuration command is “missing” on LMT and the cells won’t come up, escalate to CME before assuming the hardware doesn’t support it — nine times out of ten it’s a package-level limitation.

Field notes & common pitfalls

  • Working-mode must match the peer end. A mismatched RF-unit working mode between GU/inter-system ends is a classic conflict-alarm source.
  • Validate topology before commit. RRU network-topology/type mismatches surface as setup failures after integration.
  • Frequency/MAGROUP overlaps block cell setup — check band plans before adding U900/G900 carriers.
  • SRAN conversions touch everything at once — clock, transport, cells — so stage and verify each layer.

IP / transport & interface MOs

ObjectWhat it configures
