TCP/UDP Throughput & the Radio-Transport Boundary

On ATG the throughput story almost always crosses the radio-transport boundary: a UE can be well-served by the radio and still have the user see low throughput, because TCP window / RTT is capping the pipe. Separating a radio-limited problem from a transport-limited one is a cross-layer discipline with a few sharp tells — DL buffer occupancy, MCS/BLER cross-check, and a UDP sanity test.

Throughput ≈ window / RTT Bandwidth-delay product (BDP) DL buffer occupancy MCS/BLER cross-check UDP vs TCP

The BDP formula — what TCP can actually use

  • TCP steady-state throughput ≈ Window / RTT (per connection, before loss).
  • BDP (bandwidth-delay product) = Bandwidth × RTT — the amount of in-flight data the pipe can hold. The TCP window must be ≥ BDP to keep the pipe full.
  • Example: 10 Mbps path with 80 ms RTT → BDP = 100 kB. A default 64 kB window underfills; you see ~6.4 Mbps per connection regardless of what the radio can do.
  • On ATG, where DL radio can hit ~10 Mbps and RTT to a distant server is ~100 ms, single-connection TCP will cap well below radio capacity unless the window is tuned or multiple parallel streams are used.

DL buffer occupancy — the tell for “radio-limited vs transport-limited”

  • The eNB’s DL MAC buffer holds PDCP/RLC PDUs waiting to be scheduled on PDSCH.
  • Buffer occupancy high, scheduler actively draining: the radio is the bottleneck. Air interface is working flat out; throughput reflects MCS × Rank × RBs.
  • Buffer occupancy low / near-zero while the user complains of low throughput: the eNB is starved — transport is sending too little. The radio could carry more but isn’t being asked to.
  • Rule of thumb: if link occupancy (fraction of grants using the full RB allocation) is < 10% while the aircraft sits in healthy radio, the bottleneck is above PDCP.

MCS/BLER cross-check — eliminate the radio explanation

  • If MCS is stable and BLER is near the OLLA target, the air interface is delivering as expected; any throughput shortfall is above the radio.
  • If MCS is oscillating (OLLA chasing) or BLER is high, the radio is contributing to the shortfall regardless of transport.
  • The combination stable MCS + healthy BLER + low buffer occupancy is the signature of a transport-limited user; no amount of radio tuning will help.

UDP vs TCP — the isolation test

  • UDP has no congestion-control feedback loop — the sender pushes at the configured rate. A UDP iperf that delivers more throughput than a TCP iperf over the same path proves the air interface can carry the data; the TCP shortfall is window / RTT / loss-recovery.
  • Conversely, if UDP also underperforms (and MCS/BLER are healthy), the issue is further downstream — backhaul, SGW/PGW, or further.

Case — iperf-server migration that looked like a radio regression

Symptom
After migrating the iperf server from Denver to Melbourne, DL TCP throughput dropped from ~6 Mbps to ~2 Mbps. Initial suspicion: radio regression on the new load.
Evidence I collected
  • DL buffer occupancy ~5% during the 2 Mbps TCP run — the eNB was being fed almost nothing to send. Classic transport starvation.
  • MCS and BLER unchanged between the Denver and Melbourne runs — radio delivered the same quality.
  • Rank-2 (2C2L) usage reduced — a secondary effect of lower offered load: the scheduler had less to carry, so rank-2 engaged less often.
  • UDP iperf to Melbourne delivered ~8 Mbps over the same path, same time. Air interface could carry it.
Root cause
Longer RTT to Melbourne (~160 ms vs ~40 ms to Denver). At the UE’s default TCP window, throughput was capped by window / RTT. The radio hadn’t changed; the transport topology had.
Recommendation
Larger TCP receive window, or parallel streams, or co-locate the iperf server closer to the test region for apples-to-apples radio comparisons.

Takeaway: a throughput regression without any change in MCS or BLER is almost always transport. Buffer occupancy is the one metric that makes it obvious.

Pitfalls I stay aware of

  • Comparing TCP runs across different RTTs and calling the difference a radio regression.
  • Not capturing buffer occupancy — without it the radio-vs-transport question stays open.
  • Chasing rank-2 share as a problem — rank adapts to offered load, so low rank-2 with low offered load is a symptom, not a cause.
  • Forgetting the UDP sanity test — one UDP iperf settles the air-interface question.
